# Security

Sluss must fail closed. The early core is not an authorization service. Explicit experimental commands can create staging refs and dispatch workflows, but cannot update the target branch. Do not install it with branch bypass privileges or use its current states as merge evidence.

The experimental local reference transaction is a separate library function that can update a branch in a trusted local bare repository. Its caller is responsible for authorization and exclusive control of the repository and filesystem; it is not used by the service or CLI and does not enforce the landing protocol.

The GitHub App's credentials, webhook secret, signing keys and any release secrets must not be accessible to code running in PR CI jobs. Persistent self-hosted runners can be compromised by untrusted workloads; deployment must use an isolation and cleanup strategy appropriate to the trust level of the code.

Required design work includes authenticating webhook payloads before persistence, installation-scoped access, replay protection and durable deduplication, explicit trusted workflow and check identity, least privilege, auditable evidence, policy-change invalidation, and concurrency-safe landing. Operator-controlled policies and GitHub rules must prevent PR code from impersonating the attestor or disabling required verification. Doctor must validate relevant permissions and rules, while landing must still revalidate them.

Webhook intake verifies HMAC over the raw payload and deduplicates normal GitHub redelivery IDs. GitHub's signature covers the body, not delivery or event headers, so an intercepted valid body and signature can be replayed with a different ID; deduplication alone is not cryptographic replay protection. Treat all events as hints and reconcile current state, use HTTPS at a trusted proxy, and do not expose the webhook secret or captured signed payloads. CI-shaped hints may avoid an admission wakeup after checking the signed body, but this shape check cannot authenticate the unsigned event header. Ambiguous bodies and collisions still request a full scan; missed PR events can wait until periodic reconciliation. The experimental worker retries pending work and periodically rescans; provider-level recovery is not yet validated.

Repository, ruleset, branch-protection, installation and reviewer-access event hints invalidate active batch observations and clear CI scheduling holds in the same transaction as the wakeup. Installation-wide and organization ruleset events without a repository are conservatively routed to the configured installation's single repository. Running external jobs still need cancellation and capacity reconciliation. Organization membership and team events require separate subscription and permissions, and may be unavailable; webhooks can also be delayed or missed. A replayed signed payload or forged event header can cause conservative invalidation, so protect captured payloads. Neither these hints nor periodic reconciliation replace fresh policy, reviewer and CI checks or solve provider-side races.

The App authentication helper issues separate repository-scoped tokens for observation, runner inventory, staging, and workflow dispatch. It rejects any returned permission outside the specific requested set, except GitHub’s implicit metadata-read permission, and rejects a different repository scope. It does not follow HTTP redirects. A provider response with additional permissions fails closed, even if those permissions are read-only. Its token issuance has only been tested against a local stub, not a GitHub App installation. The caller must verify that an installation and repository are authorized before requesting a token; an untrusted webhook is not sufficient authorization.

PR observations fetch all review pages and compare repeated reads. A separate helper checks reviewer identities and effective repository permissions twice, then rereads the PR. GitHub does not expose an atomic snapshot across PRs, reviews, permissions and policy; agreement between reads is not proof that the result stays current. Branch policy, related PRs and code-owner requirements still need to be checked; observations alone cannot admit or land a change.

The CI-planning admission evaluator accepts an explicit list of currently authorized reviewer IDs. The permission helper can supply that list, but the evaluator does not itself fetch permissions, implement CODEOWNERS or assert GitHub branch-rule equivalence. An approval must be independent and reference the current head; comments do not replace decisions, and authorized outstanding change requests block planning. The result is not a merge authorization.

Reconciliation persists an entire repo's queue observations and acknowledges the triggering revision in a single SQLite transaction. A newer event rejects the transaction. The database binds to the App identity, API origin, installation, repository and policy digest; a change is rejected until an explicit paused, drained migration. That migration clears current queue observations and CI-only holds, stales pending splits and investigations, and advances the reconciliation revision before the new policy can plan work. An operator must stop external workers and processes; SQLite cannot verify they have exited. The scheduler remains experimental. Keep configuration outside PR-controlled paths and restart every worker with the same new configuration.

No operation may silently fall back from exact-commit strict landing to squash or a different commit. If provider guarantees, evidence, policy identity, or update outcome are uncertain, stop and reconcile rather than land.

`doctor --config ... --capacity ... --workflow-id ...` performs read-only provider observations and checks token issuance, but still exits unsuccessfully. It samples classic branch protection with Administration read and inspects details for rulesets referenced by active branch rules. GitHub can omit [`bypass_actors`](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) when the token lacks sufficient access; an omitted list is unknown, not empty. A 403 or 404 when reading [classic protection](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection) is also unknown, not proof of absence. Repeated matching reads do not prove exclusivity of writers, complete visibility across all provider policy surfaces, or race-free authorization. Repository runner inventory excludes organization and enterprise runners. Workflow contents, runner isolation, trusted evidence and exact-commit landing remain unverified.

The diagnostic obtains the App's numeric identity using its signed JWT and compares it with visible bypass actors. It reports missing update restrictions, upstream update allowances, other bypass actors, missing direct App bypass and several incompatible or unverified classic protection settings. The experimental fresh-claim helper refuses when this conservative assessment reports a finding or lacks complete visibility. This deliberately rejects some configurations that could work, including classic-only writer restrictions, rather than asserting that they are unsafe. No findings do not establish that writers or policy administrators are exclusive, or that reviews and rules cannot change after observation; they are not permission to land.

`verify-staged-ci` records an experimental provider-observed CI candidate without requiring a branch bypass or publishing a check. Its local digest is an integrity aid rather than a signature, and an App-authenticated read does not prove that an operator policy includes every executable dependency or that its runner is isolated. `inspect-staged-ci` checks current local state only; provider changes can occur after the saved scan. The candidate is not a merge authorization and must not be substituted for a trusted positive check or strict landing protocol. A complete branch-security snapshot is still required, and missing visibility fails closed. New scoped deliveries and previously unseen conflicting deliveries atomically clear current candidate pointers, and a monotonically increasing delivery revision rejects a provider scan or experimental landing claim if a delivery or periodic scan occurs during it, even when already acknowledged. Missed or delayed provider events and changes after the final read remain unresolved. GitHub does not let an App set a check conclusion to `stale`; a successful check must not be treated as self-invalidating. See the [Checks API](https://docs.github.com/en/rest/checks/runs#update-a-check-run).

The opt-in `start-staged-check` path can create only an `in_progress` App check on a frozen staging SHA after a fresh CI-policy observation. It commits a single-send intent before the POST and never automatically retries an uncertain result. An operator-supplied matching check can be associated after repeated authenticated reads, but this does not establish request origin; late contradictory IDs remain a conflict. The App's Checks-write key and installation tokens must remain inaccessible to all PR workloads. This is not a positive attestation or merge permission. A separate cancellation path requires a direct creation receipt, a stale local candidate, repeated matching App and check observations, and a single journaled update to `cancelled`. A recovered-only creation cannot be cancelled by this path. Uncertain updates require read-only recovery rather than resending, and an event racing after the local claim can still cause an unnecessary cancellation. The opt-in service worker uses the same checks and recovers uncertain cancellations through reads only; it still depends on correct repository scoping and key isolation. Resolution of receipt conflicts and live-provider acceptance remain open.

The experimental read-only check observer verifies the repository, exact SHA, batch external ID, check-run and suite IDs, `sluss/verified` name, successful conclusion and issuing App against a JWT-authenticated App identity. It performs repeated reads and is tested against a local stub; it cannot prove the check was legitimately produced or authorize landing. GitHub can treat [`neutral` and `skipped` as passing required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#required-check-needs-to-succeed-against-the-latest-commit-sha), so Sluss's observer requires `success`. GitHub branch settings must independently bind any required check to the intended App; a check name alone is not an issuer guarantee. Sluss does not yet publish trusted attestations.

The experimental landing claim also requires repeated matching GitHub GraphQL [`reviewDecision`](https://docs.github.com/en/graphql/reference/pulls) observations of `APPROVED` for every frozen member. Null and unrecognized decisions fail closed. The field is a transient review status; it is not proof that every branch or CODEOWNERS requirement is satisfied, nor can its non-atomic reads prevent a later review or policy change. The live query has only been tried using a user credential, not the App token.

Changing the declared CI policy-file list requires an explicit paused, drained migration and an expected revision. Existing batch evidence is tied to the old revision and cannot be revived by restoring the same paths. This controls local reuse; it cannot verify that the operator listed every executable dependency or stopped external workers.

The experimental App claim requires an independently provided, frozen `TrustedCiPolicy` matching the repository, workflow, declared policy-file digest, job and suite requirements, selection policy and allowed runner IDs. This makes a changed operator policy or mismatched run a rejection, not a trusted attestation. The operator remains responsible for protecting the policy and its complete dependencies, pinning external actions, validating the test harness and isolating runners from credentials. The manifest and provider observations cannot resolve concurrent GitHub review and policy changes during a future ref update.
