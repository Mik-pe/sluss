# Security

Sluss must fail closed. The early core is not an authorization service. Explicit experimental commands can create staging refs and dispatch workflows, but cannot update the target branch. Do not install it with branch bypass privileges or use its current states as merge evidence.

The experimental local reference transaction is a separate library function that can update a branch in a trusted local bare repository. Its caller is responsible for authorization and exclusive control of the repository and filesystem; it is not used by the service or CLI and does not enforce the landing protocol.

The GitHub App's credentials, webhook secret, signing keys and any release secrets must not be accessible to code running in PR CI jobs. Persistent self-hosted runners can be compromised by untrusted workloads; deployment must use an isolation and cleanup strategy appropriate to the trust level of the code.

Required design work includes authenticating webhook payloads before persistence, installation-scoped access, replay protection and durable deduplication, explicit trusted workflow and check identity, least privilege, auditable evidence, policy-change invalidation, and concurrency-safe landing. Operator-controlled policies and GitHub rules must prevent PR code from impersonating the attestor or disabling required verification. Doctor must validate relevant permissions and rules, while landing must still revalidate them.

Webhook intake verifies HMAC over the raw payload and deduplicates normal GitHub redelivery IDs. GitHub's signature covers the body, not delivery or event headers, so an intercepted valid body and signature can be replayed with a different ID; deduplication alone is not cryptographic replay protection. Treat all events as hints and reconcile current state, use HTTPS at a trusted proxy, and do not expose the webhook secret or captured signed payloads. The experimental worker retries pending work and periodically rescans; provider-level recovery is not yet validated.

The App authentication helper issues separate repository-scoped tokens for observation, runner inventory, staging, and workflow dispatch. It rejects unexpectedly broad returned permissions or repository scope and does not follow HTTP redirects. Its token issuance has only been tested against a local stub, not a GitHub App installation. The caller must verify that an installation and repository are authorized before requesting a token; an untrusted webhook is not sufficient authorization.

PR observations fetch all review pages and compare repeated reads. A separate helper checks reviewer identities and effective repository permissions twice, then rereads the PR. GitHub does not expose an atomic snapshot across PRs, reviews, permissions and policy; agreement between reads is not proof that the result stays current. Branch policy, related PRs and code-owner requirements still need to be checked; observations alone cannot admit or land a change.

The CI-planning admission evaluator accepts an explicit list of currently authorized reviewer IDs. The permission helper can supply that list, but the evaluator does not itself fetch permissions, implement CODEOWNERS or assert GitHub branch-rule equivalence. An approval must be independent and reference the current head; comments do not replace decisions, and authorized outstanding change requests block planning. The result is not a merge authorization.

Reconciliation persists an entire repo's queue observations and acknowledges the triggering revision in a single SQLite transaction. A newer event rejects the transaction. The database binds to the App identity, API origin, installation, repository and policy digest; a change is rejected pending a safe policy migration. No production scheduler consumes these observations. Keep configuration outside PR-controlled paths and restart the service after changing it.

No operation may silently fall back from exact-commit strict landing to squash or a different commit. If provider guarantees, evidence, policy identity, or update outcome are uncertain, stop and reconcile rather than land.

`doctor --config ... --capacity ... --workflow-id ...` performs read-only provider observations and checks token issuance, but still exits unsuccessfully. It samples classic branch protection with Administration read and inspects details for rulesets referenced by active branch rules. GitHub can omit [`bypass_actors`](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) when the token lacks sufficient access; an omitted list is unknown, not empty. A 403 or 404 when reading [classic protection](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection) is also unknown, not proof of absence. Repeated matching reads do not prove exclusivity of writers, complete visibility across all provider policy surfaces, or race-free authorization. Repository runner inventory excludes organization and enterprise runners. Workflow contents, runner isolation, trusted evidence and exact-commit landing remain unverified.

The diagnostic obtains the App's numeric identity using its signed JWT and compares it with visible bypass actors. It reports missing update restrictions, upstream update allowances, other bypass actors, missing direct App bypass and several incompatible or unverified classic protection settings. The experimental fresh-claim helper refuses when this conservative assessment reports a finding or lacks complete visibility. This deliberately rejects some configurations that could work, including classic-only writer restrictions, rather than asserting that they are unsafe. No findings do not establish that writers or policy administrators are exclusive, or that reviews and rules cannot change after observation; they are not permission to land.

The experimental read-only check observer verifies the repository, exact SHA, batch external ID, check-run and suite IDs, `sluss/verified` name, successful conclusion and issuing App against a JWT-authenticated App identity. It performs repeated reads and is tested against a local stub; it cannot prove the check was legitimately produced or authorize landing. GitHub can treat [`neutral` and `skipped` as passing required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#required-check-needs-to-succeed-against-the-latest-commit-sha), so Sluss's observer requires `success`. GitHub branch settings must independently bind any required check to the intended App; a check name alone is not an issuer guarantee. Sluss does not yet publish trusted attestations.
