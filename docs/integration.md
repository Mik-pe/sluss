# Local integration builder

The experimental Rust API constructs an ordered sequence of merge commits from a local repository, a frozen base SHA and one or more frozen PR-head SHAs. It creates its own disposable clone and does not write to the source or publish a ref during construction. All input objects must be present and fetchable from the source. Only full lowercase SHA-1 commit IDs are accepted. Conflicting or already-contained heads cause the entire operation to fail.

Each merge uses Git's `merge-tree` and creates a two-parent commit with fixed author, committer, date and message. Identical inputs are reproducible for the same Git implementation and merge environment; Git versions or merge behavior can change results, so the deployment must pin and attest those inputs. Each local build command has a 10-minute wall-clock limit and a 1 MiB stdout limit; stderr is discarded. Limit and timeout failures leave the batch for operator recovery rather than classifying a PR as conflicted. On Unix, Sluss kills the command process group on these failures; a process that deliberately escapes that group or a force-killed Sluss process may need external cleanup. These limits do not bound every other Git operation. Generated objects exist in the owned temporary repository only for the lifetime of the result. The caller must preserve them before dropping it if needed.

An explicit experimental API can publish an integration to a local Git repository or to GitHub over HTTPS using an operator-supplied token. It only creates a `refs/heads/sluss/<id>` branch and uses a compare-and-swap lease requiring the ref to be absent. An existing ref at the same SHA makes retries idempotent; a different SHA is a conflict. A failed or interrupted push is read back, with inconclusive outcomes reported as uncertain. The opt-in GitHub staging worker uses this API; batch identifiers are persisted and uncertain results are checked against the staging ref before reuse. The GitHub remote and token must refer to the intended repository, and the token needs staging-branch write access. The temporary credential helper uses a private file without embedding the token; run Sluss and its credentials outside untrusted CI jobs. Authenticated staging is currently supported only on Unix. This has been exercised against local bare repositories, not a live GitHub App.

The builder and staging API do not resolve approvals, validate policies, run CI or land changes. Tests on generated commits do not authorize a target update. Interrupted-process cleanup and production integration remain open work.

An experimental policy snapshot compares explicitly named regular files at the frozen base and integration commit, and computes a SHA-256 digest over their sorted paths, modes and exact bytes. Missing, changed, symlinked, oversized or invalid paths fail closed. All declared base files are validated first. A difference in a staged file fails the batch and uses integration bisection, holding a singleton for review; no staging ref is published. A missing, non-regular or oversized base file is an operator configuration error and does not classify PRs as failed. Policy-changing PRs require a separately reviewed bootstrap procedure. This only covers files the operator selected: external actions, dynamic dependencies, branch rules, runner trust and the authenticity of the base still need separate validation. A digest is not an attestation.

The experimental `plan` and `prepare-local` CLI commands connect queue selection to a local Git staging repository. They persist the build state and policy digest, recheck the queue around Git work, and recover an interrupted deterministic build by reusing the same staging ref. A webhook can still arrive during publication, and a created ref can trigger workflows before the final database update. The caller must control that remote and its triggers. The resulting batch is testing, not attested or authorized to land.

`prepare-github` is an experimental explicit CLI path that obtains a separate, repository-scoped GitHub App token with Contents write access and checks the configured repository identity before publishing the `sluss/` ref. GitHub scopes that permission to a repository, not a branch: repository rules must protect the target branch and prevent unauthorized modification of staging refs. Before any GitHub staging push, the builder enumerates the direct workflow files in the exact integration commit, checks their `push` filters against the intended staging branch, and rejects explicit `create` triggers. A clearly different literal branch prefix or an explicit `branches-ignore: ["sluss/**"]` can prove exclusion. Unknown or ambiguous YAML, unproven glob patterns, symlinks, oversized files and unsafe triggers stop publication; the error identifies the workflow when possible. This covers files added by the PR even if omitted from the operator's policy list. The coordinator first checks the frozen base. If that base is safe and the integration introduces a deterministic unsafe or ambiguous workflow, it fails the batch and schedules bisection, holding a failing singleton for review. An unsafe base, Git inspection failure or resource limit does not classify a PR as failed. Local staging remains caller-controlled and does not perform this GitHub-specific check. The guard is not a complete scheduler boundary: events such as `workflow_run`, organization/enterprise runners and external automation are not covered, and changed provider state or other actors may still start work. Operators must control these separately. The guard inspects the integration commit; GitHub's exact behavior for all branch-creation scenarios and the command and token flow have not been tested against a live GitHub App. It does not authorize CI results or landing.
