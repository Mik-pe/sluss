# Comparing a pilot

`sluss benchmark --input /path/to/benchmark.json` compares two operator-collected cohorts. [The example](../examples/benchmark.json) is **synthetic**, not a pilot or a claim of savings. The command neither queries GitHub nor validates input completeness, reviews, checks or merge provenance. Do not use its output as merge authorization or a production acceptance decision.

Each cohort has a UTC interval `[start, end)`, completed jobs and delivered PRs. Baseline must end before or at the start of the Sluss cohort. A job must have a unique GitHub job ID, run ID, attempt, runner ID, and its actual RFC 3339 start and completion times. The full job must fit inside its cohort. Every completed job counts, including failed, cancelled, investigation and rerun attempts, regardless of whether its run delivered a PR. Jobs without a runner or actual timestamps are not measured; unresolved or missing executed jobs make the job collection incomplete. Two positive-duration jobs on the same runner cannot overlap. Times are reduced to milliseconds. Runner time is the sum of job durations, not workflow elapsed time or necessarily physical machine time when multiple runners share a host.

Each delivered PR must have a unique number and an authoritative merge time inside its cohort. `ready_at` is optional and means the first time that same version became eligible under the chosen, consistently applied ready definition; record it only if reliable. A changed head may require a new ready time under that definition. An optional `(run_id, attempt)` identifies an observed run linked by the operator to that delivery. It must exist among the cohort's jobs and its observed jobs must have completed by merge time. This association is not proof of what was tested or merged. Multiple deliveries may reference the same attempt. Unattributed deliveries are still counted; the report displays how many associations exist.

Set `jobs_complete` or `deliveries_complete` to `false` whenever the relevant population is missing, unresolved or only partially collected. Completeness is an operator assertion, not something this command can establish. Both flags must be true, both cohorts must have deliveries, and both must have nonzero recorded runner time before the command reports a percentage change. A zero baseline cannot support a ratio. The report counts distinct `(run_id, attempt)` pairs represented by completed jobs, and those with attempt greater than one as reruns. Attempts without a measured job are not counted. Median and p90 use the nearest-rank method and always show the number of available ready-to-merge samples; missing times are not treated as zero.

Choose boundaries when relevant work is drained, or otherwise account for and document boundary-crossing jobs and pending deliveries. Because this input format requires a whole job inside a cohort, it cannot represent a crossing job; mark the job data incomplete if any relevant work cannot be included. Include all comparable CI work, not just successful batches or jobs that resulted in a merge. Record the query, collection time, workflow and runner scope, missing records, ready definition and any policy or workload differences separately. A before/after percentage is descriptive, not a causal estimate; small or unrepresentative cohorts and changes in the PR mix can dominate it. Inspect latency alongside runner minutes, and do not claim the 30% pilot target from synthetic or incomplete data.
