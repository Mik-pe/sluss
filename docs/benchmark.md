# Comparing a pilot

`sluss benchmark --input /path/to/benchmark.json` compares two operator-collected cohorts. [The example](../examples/benchmark.json) is **synthetic**, not a pilot or a claim of savings. The command neither queries GitHub nor validates input completeness, reviews, checks or merge provenance. Do not use its output as merge authorization or a production acceptance decision.

An operator can collect explicit GitHub observations with an installed App and [this selection format](../examples/benchmark-selection.json):

```sh
sluss collect-benchmark --config /path/to/sluss.toml --request /path/to/selection.json > benchmark.json 2> collection-notes.txt
sluss benchmark --input benchmark.json
```

The selection names run IDs and PR numbers separately for each cohort; replace all example values. The collector reads the repository identity, every selected run and its attempts, complete paginated job lists and each selected merged PR through the App. It rechecks the latest run and each PR and rejects inconsistent identities, incomplete runs or PRs not merged to the configured target. Selected IDs are unique across cohorts; limits are 100 runs and 100 PRs per cohort, 200 attempts and 10,000 jobs per request. Jobs crossing a boundary or lacking runner identity or actual times are excluded and identified in stderr, as are jobs wholly outside the interval. Failures, cancellations and reruns are not excluded just because they failed; jobs without measured runner time cannot be counted. The tool does not discover the complete population, infer exact ready times or link a run to a delivered PR. It always sets both completeness flags to `false`, so the report cannot claim a savings percentage until an operator has independently established completeness and updated the file. A missing crossing job cannot be represented by this format; adjust boundaries and recollect instead of treating it as complete. App access, data retention, deleted runs and provider races can still make collection incomplete; API reads are not an atomic GitHub snapshot. Collection has been tested against a local provider stub, not a live App or Ugla pilot. A separate read with a user credential on 2026-10-28 observed GitHub’s [job 122635685974](https://github.com/Mik-pe/sluss/actions/runs/40633695016/job/122635685974) with a runner ID and a 94-second start-to-finish interval, and verified the merged-status fields of an open PR. Those reads check response shape only; they do not execute the App collector or establish a pilot result.

For new reconciliations, Sluss also keeps local admission observations by PR head, base and review-evidence digest. `sluss admission-history --pr <number>` reads the latest 100 observations without migrating the database. A new head, changed evidence or base, or removal ends the previous observation; a later readmission starts another. Repeated unchanged reconciliations update the last observation rather than inventing a new start. Older data is not backfilled, local wall-clock reversals mark affected observations uncertain, and webhook delivery and reconciliation can be delayed. The first local observation is not the exact moment a PR became ready, and neither an open record nor two matching reads prove continuous eligibility.

To add these observations to the Sluss cohort, pass `--admission-db /path/to/sluss.sqlite` to `collect-benchmark`. The database must have the same repository and full App/reconciliation policy binding. Only observations from the current admission-policy epoch are eligible; changing away from and back to the same policy does not revive earlier observations. The collector rechecks the binding and epoch after reading the local records. For each selected merged PR, the collector matches GitHub’s currently returned head SHA with a local observation whose first and last observations precede the reported merge, whose locally observed end is after it or absent, and whose clock was not marked uncertain. Matching uses current provider data and a trusted local database; it does not prove the head or eligibility at merge, and can miss unobserved or delayed changes. Ambiguous boundary times are excluded. The result is stored as `observed_ready_at`, separate from an independently established `ready_at`; baseline deliveries are not automatically annotated. The report shows observation-to-merge samples separately and does not treat them as exact ready-to-main latency. Both completeness flags remain false and no run-to-PR association is inferred.

Each cohort has a UTC interval `[start, end)`, completed jobs and delivered PRs. Baseline must end before or at the start of the Sluss cohort. A job must have a unique GitHub job ID, run ID, attempt, runner ID, and its actual RFC 3339 start and completion times. The full job must fit inside its cohort. Every completed job counts, including failed, cancelled, investigation and rerun attempts, regardless of whether its run delivered a PR. Jobs without a runner or actual timestamps are not measured; unresolved or missing executed jobs make the job collection incomplete. Two positive-duration jobs on the same runner cannot overlap. Times are reduced to milliseconds. Runner time is the sum of job durations, not workflow elapsed time or necessarily physical machine time when multiple runners share a host.

Each delivered PR must have a unique number and an authoritative merge time inside its cohort. `ready_at` is optional and means the first time that same version became eligible under the chosen, consistently applied ready definition; record it only if reliable. A changed head may require a new ready time under that definition. An optional `(run_id, attempt)` identifies an observed run linked by the operator to that delivery. It must exist among the cohort's jobs and its observed jobs must have completed by merge time. This association is not proof of what was tested or merged. Multiple deliveries may reference the same attempt. Unattributed deliveries are still counted; the report displays how many associations exist.

Set `jobs_complete` or `deliveries_complete` to `false` whenever the relevant population is missing, unresolved or only partially collected. Completeness is an operator assertion, not something this command can establish. Both flags must be true, both cohorts must have deliveries, and both must have nonzero recorded runner time before the command reports a percentage change. A zero baseline cannot support a ratio. The report counts distinct `(run_id, attempt)` pairs represented by completed jobs, and those with attempt greater than one as reruns. Attempts without a measured job are not counted. Median and p90 use the nearest-rank method and always show the number of available ready-to-merge samples; missing times are not treated as zero.

Choose boundaries when relevant work is drained, or otherwise account for and document boundary-crossing jobs and pending deliveries. Because this input format requires a whole job inside a cohort, it cannot represent a crossing job; mark the job data incomplete if any relevant work cannot be included. Include all comparable CI work, not just successful batches or jobs that resulted in a merge. Record the query, collection time, workflow and runner scope, missing records, ready definition and any policy or workload differences separately. A before/after percentage is descriptive, not a causal estimate; small or unrepresentative cohorts and changes in the PR mix can dominate it. Inspect latency alongside runner minutes, and do not claim the 30% pilot target from synthetic or incomplete data.

For operational accounting outside a full benchmark collection, `sluss --db PATH collect-rerun-metrics --batch-id ID --attempt N --config CONFIG --capacity CAPACITY` explicitly reads a completed attempt twice through the GitHub App. It checks the directly acknowledged run, frozen workflow and commit and a previously recorded first-attempt host, then records completed, host-checked job timings idempotently. It works after reservation release if that original measurement remains available. `sluss metrics` reports these observed rerun jobs and minutes separately. The command does not automatically discover attempts; omitted reruns and unobserved work still make metrics incomplete. If a later observation conflicts with a recorded job, collection fails and the earlier measurement remains; investigate it before relying on the totals. A recovered or conflicting receipt, missing original measurement, changed host mapping or incomplete attempt is rejected. This is accounting, not CI evidence, capacity release or merge authorization, and has been tested against a local provider stub rather than a real App.
