# Verification and landing protocol

This is a design contract, not a claim that the protocol is implemented.

1. Reconcile each PR's current head, independent review and blockers. Freeze the target base, ordered PR numbers and heads, and policy identity in a batch.
2. Build the integration in an isolated workspace. Record every input, Git behavior and the exact resulting commit. Conflicts fail the batch without changing the target.
3. Start and reconcile trusted CI for that exact commit. Bind evidence to the repository, workflow identity, run and attempt, commit, required jobs and policy; never trust a result supplied by PR code as Sluss's own attestation.
4. Recheck current PR heads, approvals, blockers, target base, permissions and policy. Any relevant change invalidates the batch. A successful test alone never authorizes landing.
5. Publish only with a provider-supported atomic update conditioned on the expected target and a compatible fast-forward, preserving the exact verified commit. Abort on uncertainty or any failed condition. After ambiguous network failure, read back the target and reconcile before retrying. A full proof must cover review/policy changes concurrent with landing, not just a head SHA comparison.

GitHub's ref-update and branch-protection semantics, including concurrent writers and changes to review or policy, must be verified end to end before strict mode is enabled. If the guarantees cannot be established with the available APIs and configured writer restrictions, strict mode must refuse to operate. A generic non-force ref update alone is not proof of an exact expected-old-value comparison; GitHub's [update-ref API](https://docs.github.com/en/rest/git/refs#update-a-reference) does not document an expected-old-SHA parameter.

GitHub's separate [GraphQL `updateRefs` mutation](https://docs.github.com/en/graphql/reference/git#updaterefs) documents atomic multi-ref updates and `beforeOid` preconditions, with `force: false` disallowing non-fast-forward updates. On 2026-10-28, probes using a user credential and disposable, unprotected branches in this repository observed: a wrong staging precondition left both refs unchanged; matching conditions advanced the target to the exact staging SHA; stale target preconditions were refused even when the current target was an ancestor of staging; and a non-fast-forward was refused with `force: false`. GitHub returned a generic GraphQL error for each rejected request. The branches were deleted after the tests. This is evidence for a potential transport, not verification with an App token, protected branches, bypass rules, concurrent review or policy changes, or an ambiguous response. In particular, the generic error must not be classified as a definite rejection or blindly retried. `doctor` can inspect the GraphQL schema read-only; the presence of fields does not prove permissions or behavior. No GraphQL mutation is wired into Sluss.

The experimental `local_refs::compare_and_advance` library function exercises a smaller Git mechanism in a trusted local SHA-1 bare repository. It verifies the staging SHA and the expected old target while holding both ref locks, refuses symbolic refs, checks commit ancestry, and advances to the exact staging commit using Git's [reference transaction](https://git-scm.com/docs/git-update-ref). It is not connected to the service, CLI or GitHub, and does not check reviews, CI, policy or authorization. Its caller must control the Git executable, repository configuration, object database, filesystem and ref writers. The checks cover values while locks are held, not an ABA change, a concurrent policy or review change, or a later writer. It has no durable write journal: an uncertain outcome must not be treated as success or automatically retried, and a forcibly terminated Git process can leave locks that require careful reconciliation. A local transaction does not establish a GitHub compare-and-swap capability.

The separate experimental `LandingJournal` records a frozen prospective GraphQL operation in SQLite WAL with full synchronization. It serializes unresolved intents per repository and target within the same database, returns the immutable plan to the one worker that claims it, and does not allow a claimed intent to be cancelled or reclaimed after restart. The generated request compares both the frozen target and staging refs with `force: false`. A trusted transport may record a matching successful direct response and its digest; errors, partial responses, lost responses and later readback are not acknowledgements. `clientMutationId` correlates a response and is not an idempotency key. There is currently no mechanism to resolve an uncertain intent, and separate databases or unmanaged writers are not serialized. The journal neither sends requests nor establishes the authenticity of its input digests, Git ancestry, fresh admission, branch policy or CI evidence. It is not connected to the service or CLI and cannot authorize a merge. A production integration must atomically bind it to current trusted batch evidence and define safe reconciliation before enabling landing.

An experimental batch-bound journal path derives its admission and CI digests from the same database transaction as preparation. It requires the current local base and heads, frozen review evidence, no pause or pending reconciliation, the frozen workflow path, a direct dispatch receipt and a complete successful recorded CI snapshot with no conflict marker. Claiming repeats those checks and compares the entire resulting plan in a write transaction; the unbound claim API refuses a batch-bound intent. These checks only bind previously observed data. They do not verify the repository node ID, provider freshness, trusted workflow contents, review or policy races, or anything that changes after the claim. No journal path is connected to a provider write.

A separate experimental App helper refreshes each included PR, reviews and reviewer permissions against the frozen admission evidence and operator policy. It reads the target and staging refs around the scan, refreshes the first Actions attempt and complete job list twice, reads the latest run around those observations, and checks the installation's numeric repository ID and GraphQL node ID. The resulting provider snapshot is compared with the frozen CI record inside the claim transaction. Changed inputs, a rerun, an incomplete or different run, or pending local reconciliation stop that claim. These reads are not an atomic GitHub snapshot: a later push, rerun, revoked review or policy change can still occur, so this is not trusted CI attestation or landing authorization. The lower-level local-only claim remains available for development and must not be used as a provider freshness check. This helper has only been tested against a local GitHub stub and is not connected to a GitHub write or the service.

A failed group may be split deterministically; each resulting group requires its own integration and fresh verification. A singleton failure is reported for investigation. Recovery uses durable operation identifiers and current provider state; duplicated webhooks and uncertain responses must not create duplicate work or unsafe updates.

The experimental GitHub client can read a specific Actions run attempt and its paginated jobs twice. It rejects changed snapshots, mismatched repository, run, attempt or commit identities, and incomplete or duplicate job records. These reads follow the GitHub [run-attempt](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run-attempt) and [attempt-jobs](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt) APIs. These provider observations do not establish trusted workflow contents, bind a policy digest, authorize a merge, or replace a final recheck. A later retry can supersede an attempt, and a partial rerun may lack required jobs; consumers must fail closed.

The experimental scheduler can persist a frozen dispatch plan and its physical-host reservation in one database transaction. A single worker may move the plan from prepared to sending; after that transition, a crash or ambiguous HTTP response must be reconciled with the provider, never blindly retried. A recorded run retains the reservation through restarts until the caller confirms that exact run can no longer consume capacity. This journal does not itself dispatch a workflow, authenticate observations, prove runner placement, or resolve ambiguous starts; a stuck uncertain intent may therefore require operator intervention. Deployments must not treat the reservation as effective capacity control until the provider workflow is actually bound to the reserved host.

The experimental GitHub client can explicitly dispatch a prepared intent using a separate installation token scoped to Actions write and contents read. It checks the token's App and API origin, repository identity, and staging ref before durably claiming the intent and sending a single request using API version 2026-03-10. The request sets `return_run_details=true` to request GitHub's run ID; a returned run ID is saved as a receipt, not trusted evidence. An absent, malformed or failed response remains uncertain and is never automatically retried. The manual command and optional worker share this path, which has only been tested against a local stub. The caller must ensure staging refs cannot be changed between the preflight and execution, avoid workflows triggered prematurely by ref creation, verify workflow policy and the observed exact SHA, and bind jobs to reserved physical capacity. The provider's [workflow dispatch endpoint](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event) requires Actions write permission. Until those conditions and live-provider recovery are verified, this API does not authorize landing or establish effective resource scheduling.

For a saved receipt, the experimental recovery API reads the latest run around two complete reads of attempt one. It binds the run only when repository, head repository, workflow, branch, commit and dispatch event match the frozen plan and the latest attempt remains one. A changed or rerun workflow is rejected for later reconciliation. This does not prove the policy, prevent a later rerun, verify runner placement or release the reservation; those checks must precede any capacity reuse.

An experimental batch planner freezes an ordered set of reconciled queue entries in one SQLite transaction. It honors pause, pending repository reconciliation, the configured active-batch limit and existing live batch membership. A GitHub reconciliation reads the target branch around the PR scan and requires each relevant PR base to match. Its target SHA and queue update commit in the same transaction; a changed base invalidates older active batches and obsolete bisection work. Planning, preparation and batch-bound dispatch reject a different recorded base. These are sampled provider observations: a branch may change after the scan or an event may be missed. Manual dispatch refreshes admission and compares the bound target and base around its staging-ref read; landing still requires a final independent check. Opt-in staging and dispatch workers can continue a planned batch.

A batch-bound dispatch can reserve host capacity and its intent in the same database after checking the frozen integration SHA, candidate heads, repository binding, pause and pending reconciliation. The same checks run atomically when a worker claims the dispatch; a still-prepared intent can be cancelled and its reservation retired. An event can still arrive after the claim, and provider changes after the last scan, provider policy, staging-ref protection and runner placement are not yet fully bound to this transaction. This is not sufficient to authorize CI as merge evidence. Generic unbound reservations remain low-level APIs and are not worker orchestration.

Reconciliation now records a digest of the observed PR, reviews and reviewer permissions for each admitted candidate. Planning freezes those digests, and batch-bound dispatch checks that they still match. A changed observation invalidates affected batches atomically even if the PR head is unchanged; a later unchanged scan does not. These observations are not atomic at GitHub, and CODEOWNERS, branch rules, trusted CI policy and a final landing recheck remain required.

The experimental planner also offers a per-candidate debounce interval. It persists the time of the latest head or admission-evidence change; an unchanged scan leaves that time intact and a process restart does not reset it. Candidates still within their interval are skipped so other stable work can proceed. The interval uses the host wall clock and requires a correctly maintained clock. A separate collection window waits after the oldest eligible candidate finishes debouncing, unless the batch is full. It uses persisted stability timestamps and survives restart. Bisection halves bypass this window. An optional worker calls this planner using the repository policy and target bound by reconciliation; concurrent workers share the same transactional limits. Separately enabled staging and dispatch workers can continue planned batches.

Reproducible integration failures enter durable left-to-right bisection. Pending halves keep their frozen heads and admission evidence, take precedence over ordinary queue selection, respect the active-batch limit, and are discarded if their inputs change. A failed singleton is shown by `sluss queue` and is held until its head or admission evidence changes. A caller using this integration-failure path must classify the failure as reproducible; unknown infrastructure failures must not be interpreted as a bad PR. Separately, the opt-in CI-only investigation described below treats provider failures as experiments, not classification.

The experimental dispatch client passes the reserved host's `sluss-host-*` label as the `sluss_host` workflow input. [The example workflow](../examples/github-actions/sluss-ci.yml) illustrates a single job targeted at that label. A separate placement check compares GitHub's observed runner ID with operator-supplied IDs for that physical machine and rejects multiple executable jobs for a single reservation. This is a detection mechanism, not enforcement: a trusted workflow, unique host labels, accurate runner-to-machine mapping, rules preventing unauthorized reruns, and isolated self-hosted runners are prerequisites. Placement is checked by the optional bounded release path; it is not CI attestation.

Before manual or automatic dispatch, the client obtains a separately scoped Administration-read token and reads the repository runner register twice. It rejects changed or incomplete inventories, mismatched runner IDs and labels, and overlapping configured host IDs. Dispatch selects only a host whose entire configured slot budget was observed idle and online; another busy host does not block it. A previously prepared reservation stays on its original host and cannot dispatch while that host is ineligible. The stricter doctor and bounded-release checks still require all configured hosts idle. Configured runner IDs are also used for placement observation. GitHub's repository endpoint only covers repository-configured runners; organization and enterprise runner registrations and actual physical colocation still require independent verification. The inventory can change immediately after the check, so this does not yet prove safe capacity control.

Scheduling-delay intervals are recorded when a batch-bound reservation first observes insufficient eligible capacity and end when that same request later obtains or regains an eligible reservation. An open interval survives process restart; repeated polls do not reset it, changed pool requirements start a new interval, and a backward wall-clock sample is discarded. Completed intervals are grouped under every requested pool. They include polling gaps, service downtime or pauses and do not identify which pool was saturated. Incomplete intervals and requests not attempted by the scheduler are excluded. These intervals are separate from runner time and are not a full ready-to-main latency measurement.

Completed job observations with confirmed configured runner IDs can be recorded as metrics. Each job is identified by repository and job ID; repeated observations with identical timestamps are idempotent, while conflicting immutable data fails closed. Runner time is the sum of job start-to-completion intervals, not workflow queue or wall time. Current totals cover only observed first-attempt completed jobs, and are not a baseline comparison, CI attestation or merge evidence.

A dispatch freezes its exact required GitHub job names. Once a provider run is observed, Sluss can persist a comparison only if the batch and its admission evidence remain current, the exact run identity matches, host placement is observed, and every required job reports success. The completed observation stores the run and normalized per-job snapshot, together with the observed runner; `ci-evidence` displays the historical record without claiming trust. A contradictory later complete snapshot creates a durable conflict and blocks CI-only completion or bounded release, even after restart. It invalidates active dependent batches and pending investigation work, marks those investigations stale and clears their old CI scheduling holds; external jobs still require reconciliation. Legacy summaries without original job data remain summaries and are not backfilled from a later read; automatic CI bisection requires the full recorded snapshots. Missing, skipped, duplicated or mismatched jobs fail closed. A failed workflow is recorded as a failure observation, without automatically blaming a PR. These records do not establish workflow trust, publish an attestation, or authorize landing. Old preview dispatch records without required job names fail closed and require explicit recovery.

The optional stale-run worker retires unstarted reservations for invalidated batches and, together with the `cancel-stale` command, identifies only known workflow runs bound to invalidated batches. They verify provider run identity, durably claim a single normal cancellation request, and keep the physical-host reservation. An interrupted or ambiguous request remains uncertain; repeated scans read provider state but do not blindly resend. This is tested against a stub and does not resolve unknown run IDs, guarantee immediate runner termination, or release capacity.

The experimental selective planner uses operator-owned exact-file and directory-prefix rules plus a dependency graph. It expands changes to dependents, treats both sides of renames as changes, includes changed submodule pointers even when repository configuration would hide them, and selects the full configured suite for unknown paths, CI/Cargo/Git policy files, empty diffs, unrepresentable change lists or any affected component without configured suites. The selection algorithm version participates in the policy digest; the current v2 refuses new staging or dispatch using v1 selections, and a bound preview database requires the explicit drained migration described below. Already dispatched CI-only runs remain historical observations and never authorize landing. Correctness still depends on a complete operator-maintained graph and trusted suite definitions. A prepared batch can freeze that selection together with its base, integration SHA and operator policy digest. Batch-bound dispatch requires the same parsed policy and checks the frozen selection when reserving and claiming; it sends sorted suite names as the `sluss_suites` input. A batch with no selection dispatches `full`. The sample workflow deliberately implements only `full` and rejects selective inputs. Policy files and suite mappings must be operator controlled, and a supplied input does not prove that the workflow executed those suites. Selection is not CI evidence or landing authorization. Existing preview dispatch records lacking suite names fail closed and require explicit recovery.

An optional dispatch observation worker periodically rereads accepted and already observed receipts, with backoff on failures. It skips invalidated batches, checks provider identity and host placement, and records current CI observations and idempotent completed-job measurements. It does not create or retry dispatches, prove trusted policy, release reservations, publish attestations, or authorize landing. This path has only been exercised against a local GitHub stub.

Before claiming a batch-bound dispatch, Sluss reads the workflow registration twice and requires an active workflow with a valid path. That exact path must appear in the file list frozen atomically with the batch's policy snapshot at staging. The claim and workflow-path binding commit together before a request can be sent. Later run observation, uncertain-send recovery, cancellation and CI-only comparison reject a different reported path whenever a binding exists. Older in-flight records without a binding remain recoverable as historical CI-only observations, but do not start automatic CI bisection. Missing, changed or unstable registration and missing batch lists stop the send, leaving any prepared reservation for explicit cancellation or retry. A previously staged preview batch without a frozen list must be rebuilt; the paused same-mode `migrate-selection --discard-unstarted` path can invalidate it after its reservation is reconciled. This preflight cannot prove the provider will execute the same workflow later, cover undeclared dependencies, establish runner isolation or replace trusted attestation. The provider can change state immediately after the reads.

Manual batch dispatch schedules a fresh reconciliation before it reserves capacity. It then checks the observed target branch on both sides of the staging-ref lookup and compares it to the batch's frozen base and the reconciled branch. Only the still-current batch can be claimed; the generic unbound dispatch API cannot send a batch-bound intent. The branch or approvals may still change after the final read, and no provider observations constitute attestation or landing authorization. Failed pre-claim checks retain any prepared reservation until retry or explicit cancellation.

The optional automatic planner generates unique batch IDs and uses the last reconciled target, App identity and queue policy. It waits while paused, while reconciliation is pending, or while the active-batch limit is reached. The first automatic pass freezes planning settings in the database; conflicting manual and automatic planners fail closed, and an explicit settings migration is not yet implemented. Existing active plans survive restart and appear in `sluss status`; an invalidated plan is not revived. Planning alone does not stage or run CI.

The optional GitHub.com staging worker refreshes admission, fetches the target and PR head refs with a repository-scoped read token, and rejects any ref that differs from the frozen inputs. It builds in temporary repositories and publishes using a separate Contents-write token; credentials are not placed in remote URLs, and authenticated Git redirects are disabled. The complete operator-declared policy-file list is bound to the database, and changed lists fail closed pending explicit migration. A stale fetched ref schedules reconciliation. Repeated preparation reconstructs the same commit and reads the staging ref back rather than overwriting another commit. Local Git tests exercise fetching, conflicts and interrupted preparation, but live App permissions, provider behavior and branch protections remain unverified.

The optional dispatch worker selects staged batches without an already claimed intent and uses the same reconciliation, policy, inventory, reservation and staging-ref checks as manual dispatch. It tries later batches when an earlier batch cannot reserve an eligible host, so a prepared reservation pinned to a busy machine does not stall an independent host. Each candidate receives a fresh provider reconciliation; provider or policy errors still stop the pass. Concurrent workers cannot both claim an intent. `Sending`, accepted and observed records survive restart and are not dispatched again; uncertain requests remain for reconciliation. Capacity is released only by the separately enabled bounded CI-only path; unattended throughput and live-provider recovery remain unproven.

For an uncertain send, an operator can provide a candidate run ID for recovery. Sluss rereads that run and its first attempt, verifies workflow, repository, event, branch and exact commit against the frozen intent, and only then associates the ID with the existing reservation. This operation never resends the POST or releases capacity. Its provenance is stored as `recovered`; a direct POST response is stored as `direct`. Matching metadata cannot prove the uncertain POST created a recovered run, so it is not trusted attestation and cannot authorize landing. Older records without source metadata remain unknown.

Optional CI-only completion atomically retires a batch after a completed provider observation with a direct dispatch receipt and unchanged inputs. The queue holds those exact heads, admission digests and target base for either success or failure, and clears the holds when the target changes; operators can clear a completed batch's holds using `retry-ci`. This is scheduling state, not per-PR status, trusted evidence or merge permission. It does not classify infrastructure failures as PR failures. The reservation is retained unless bounded release is enabled; GitHub permits later workflow reruns, so a completed snapshot alone cannot prove future capacity safety. Recovered and unknown receipt sources cannot complete automatically.

With the separately enabled CI investigation, a directly received failed multi-PR run creates two durable frozen halves in the same transaction as completion. Both halves must finish with unchanged admission and base, and matching installation, repository, frozen workflow ID and path, policy, required jobs, suite selection and selection policy. Their identity and policy must also match the parent; the parent may have selected a subset, while both halves use all suites from the configured verification policy. Only a failure paired with a success continues into the failed half. A singleton is marked `needs-review`; paired failures, paired successes, other conclusions or mismatched plans are `inconclusive`, and changed inputs make the investigation `stale`. Admission reconciliation atomically marks investigations with changed frozen inputs stale, cancels unplanned descendants and invalidates active descendants, including when the changed PR was in a previously successful sibling. A subgroup integration conflict makes the CI comparison inconclusive while its separate conflict bisection can continue. Terminal results propagate to active ancestor investigations. Already-started external runs still need the normal cancellation and reservation recovery paths. These observations cannot establish which change caused a failure or authorize a merge. The database binds the investigation setting across workers; changing it requires a future migration. Live provider behavior and automated recovery remain unproven.

The optional bounded release path accepts one configured runner and one slot per physical host, with each global pool budget at least the sum of all declared host capacities for that pool. It checks the exact completed first attempt and observed runner placement, reads repository runner inventory twice, rereads the run, then atomically releases the reservation. Since GitHub executes one job at a time per runner, the worst-case budget remains sufficient even for later reruns, provided the operator's host mapping is complete, no additional runners share a physical host, all work stays inside declared host pool capacities, no untracked workloads use those global pools, and job isolation or cleanup prevents lingering work. Provider inventory cannot verify these physical conditions. The topology is frozen in the database after the first release; no migration is implemented. The same checks may release a directly identified run from an invalidated batch once the provider reports it complete, including a previously unobserved receipt; completed jobs on a confirmed runner are recorded as metrics before release. If all jobs were skipped or no jobs exist, no placement is asserted; a completed executable job without a runner identity is rejected. Unknown or recovered run identities remain reserved. The path is tested with a local stub only and is not merge authorization.

Automatic staging may calculate selective suites from the integration commit using an operator-owned verification policy. Staging mode and the parsed policy digest are bound to the database. The frozen base, integration SHA, selected suites and policy digest commit in the same transaction as the transition to `Testing`, so a restart cannot expose a partially selected batch to dispatch. Conflicting modes or policies fail closed. With all workers stopped, an operator can pause and drain the database, then invoke `migrate-selection` using the exact expected old mode and a validated new policy or full mode. It rejects reservations and unresolved dispatches and, unless `--discard-unstarted` is explicit, active batches. With that flag it invalidates active batches so their PRs can be planned again. It marks old CI investigations and their pending descendants stale, clears their scheduling holds, and records the old and new mode and discarded batch count atomically. Unrelated integration-conflict splits and historical observations are retained. An operator must stop external staging processes because SQLite cannot prove they have exited. Dispatch independently reloads and compares the policy. The supplied workflow must implement the selected suite names and remain trusted; selection is not an attestation.
