# Verification and landing protocol

All SQLite write entry points, including the queue, webhook inbox, scheduler, capacity migration and landing journal, require WAL and set `synchronous=FULL` on their own connection before writing. They verify both settings and fail if WAL cannot be enabled; in-memory databases are therefore unsuitable for these durable paths. This preserves the intended ordering of committed intents and external requests under SQLite’s sync contract. It has not been tested by cutting power, and depends on the filesystem and storage honoring synchronization; backups must include a consistent SQLite snapshot including its WAL. See [SQLite’s synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous).

This is a design contract, not a claim that the protocol is implemented.

1. Reconcile each PR's current head, independent review and blockers. Freeze the target base, ordered PR numbers and heads, and policy identity in a batch.
2. Build the integration in an isolated workspace. Record every input, Git behavior and the exact resulting commit. Conflicts fail the batch without changing the target.
3. Start and reconcile trusted CI for that exact commit. Bind evidence to the repository, workflow identity, run and attempt, commit, required jobs and policy; never trust a result supplied by PR code as Sluss's own attestation.
4. Recheck current PR heads, approvals, blockers, target base, permissions and policy. Any relevant change invalidates the batch. A successful test alone never authorizes landing.
5. Publish only with a provider-supported atomic update conditioned on the expected target and a compatible fast-forward, preserving the exact verified commit. Abort on uncertainty or any failed condition. After ambiguous network failure, read back the target and reconcile before retrying. A full proof must cover review/policy changes concurrent with landing, not just a head SHA comparison.

Scoped webhook intake distinguishes CI observation hints from admission changes. After signature verification, a `check_run`, `check_suite`, or `workflow_run` header with the matching object in its signed payload and without obvious PR, review, push, or security fields advances the delivery clock and invalidates current CI candidates, but does not replace a pending admission revision or schedule a new admission scan. After a new matching delivery commits, a process-local notification wakes the CI observer after at least five seconds. Hints coalesce; duplicates and collisions do not notify. Failed observation passes retain exponential backoff and ignore notifications until the backoff expires. The observer also scans on startup and polls at least every 60 seconds on successful passes. Notifications are not durable or shared across processes: a lost notification, missing event or webhook delivered to another process is recovered by polling. The payload is never treated as a CI result. Any ambiguous body, distinct delivery-ID collision, unscoped receiver, or raw `Inbox::record` call retains the full admission wakeup. PR and security events still invalidate the current scan, and periodic scans recover missed PR events. GitHub documents these [webhook payloads](https://docs.github.com/en/webhooks/webhook-events-and-payloads); their headers are not signed, and checking the body shape does not authenticate the event type. If an event is delayed or missed, a CI hint is no longer an indirect admission wakeup, so queue changes can wait until the next scan. Live App behavior and event rates remain unverified.

Queue discovery requests open pull requests for the configured target branch using GitHub's [base filter](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests). It validates the state, base branch and repository ID in every returned listing entry, compares repeated paginated listings, and performs a final listing after the PR scan. A retargeted PR is removed on reconciliation, invalidating affected batches; a retargeted PR can re-enter after a later scan. Webhooks and periodic scans remain necessary, and repeated reads cannot prevent changes after the last observation. The filter and response shape have been read with a GitHub user token; the App path remains stub-tested.

GitHub API requests made through one running App instance share an in-memory rate-limit gate. Configured `serve` processes and CLI commands that update the queue or its journals also store the gate in their queue SQLite database and check it before each API request, so those processes sharing that database and restarted services observe the same deadline. A 429, a 403 with a retry header or a rate-limit message, or a response reporting zero remaining capacity defers later requests until the indicated retry/reset time; absent usable guidance defaults to at least one minute. Ordinary permission-denied responses do not pause unrelated operations. In-flight requests may finish. Inspection-only CLI commands and processes using a different database do not share the durable gate. GitHub fetch and staging push check the known gate immediately before starting, but Git transport rate-limit responses are not detected and a gate can close after the check. Inspection commands remain read-only and do not create or modify a rate-limit table. Database errors fail the affected service request closed; if recording a limit fails, other processes cannot learn it from the database. The durable deadline uses wall-clock time: a backward clock before the recorded observation fails closed, but a forward clock jump can cause early resumption. The two implemented GraphQL read paths also recognize rate-limit errors in HTTP 200 responses and persist the same gate. Other GraphQL errors remain failures without triggering a rate-limit pause; future GraphQL operations must apply the same handling. GitHub documents the [GraphQL limit responses](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#exceeding-the-rate-limit); live App behavior remains unverified. Sluss rechecks the gate before claiming a one-shot write. If another worker closes the gate between that check and the send, the claimed intent remains uncertain even when this process did not send it; it is not blindly retried. Existing durable one-shot semantics still apply to writes after any ambiguous provider response. See [GitHub rate-limit handling](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit).

`sluss status` reports the saved shared rate gate as uninitialized, open, deferred, clock-blocked, indefinite or unavailable. This is a read-only inspection of the gate record; it cannot show process-local limits or gates in other databases. A backward clock fails closed; an indefinite deadline or unavailable database requires investigation rather than an automatic reset.

A PR assessment or queue reconciliation may use bounded, in-memory ETag caching across its repeated PR and paginated review reads. Only an authenticated conditional request for the same URL within that operation can reuse a cached response after `304 Not Modified`; missing or malformed ETags fall back to full reads, and an unsolicited 304 fails. The cache is discarded between operations, is never shared across tokens, and has an 8 MiB body limit. GitHub states that correctly authenticated 304 responses do not consume the primary REST rate limit ([GitHub REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)); requests and secondary rate limits still apply. User-token probes against this repository returned 304 for a PR and its reviews; App-token behavior remains stub-tested. ETags are provider assertions and do not make the observation atomic.

A queue reconciliation reads each PR and its reviews independently on both sides of a shared permission scan. It reads each distinct decision reviewer's repository permission twice per scan, even when the same reviewer appears on many PRs, and associates only that PR's reviewers with its evidence. Conflicting identities, changed observations or permissions and duplicate PR numbers abort the entire scan without acknowledging the queued work. The bounded scan accepts at most 10,000 PRs, 100 decision reviewers per PR, 10,000 distinct reviewers and 50,000 total review records. These are repeated observations, not an atomic provider snapshot; changes after the last read remain possible. This reduces permission calls but does not reduce the per-PR snapshot reads.

CI admission checks current-head approvals, change requests and dismissals from independently authorized reviewers. Ordinary review comments and pending reviews are still read as part of the provider snapshot, but are excluded from the admission digest and do not require reviewer-permission lookups. A comment alone therefore does not invalidate a frozen batch. Relevant decisions, reviewer permissions, PR metadata and blockers are still rechecked. The digest is versioned: stop old Sluss workers before upgrading, because mixed versions would disagree. The first reconciliation after upgrading from the earlier digest invalidates incompatible old batch evidence and may require new CI. Webhook hints can still invalidate a saved CI candidate; these observations are not merge authorization.

GitHub's ref-update and branch-protection semantics, including concurrent writers and changes to review or policy, must be verified end to end before strict mode is enabled. If the guarantees cannot be established with the available APIs and configured writer restrictions, strict mode must refuse to operate. A generic non-force ref update alone is not proof of an exact expected-old-value comparison; GitHub's [update-ref API](https://docs.github.com/en/rest/git/refs#update-a-reference) does not document an expected-old-SHA parameter.

GitHub's separate [GraphQL `updateRefs` mutation](https://docs.github.com/en/graphql/reference/git#updaterefs) documents atomic multi-ref updates and `beforeOid` preconditions, with `force: false` disallowing non-fast-forward updates. On 2026-10-28, probes using a user credential and disposable, unprotected branches in this repository observed: a wrong staging precondition left both refs unchanged; matching conditions advanced the target to the exact staging SHA; stale target preconditions were refused even when the current target was an ancestor of staging; and a non-fast-forward was refused with `force: false`. GitHub returned a generic GraphQL error for each rejected request. The branches were deleted after the tests. Four additional trials launched two competing `updateRefs` requests against the same expected base and two distinct descendant staging commits; each observed one acknowledged winner, the exact winning target SHA and unchanged staging refs. All twelve temporary refs were deleted and their absence confirmed. The last two trials used the repository script below, including independent ancestry checks; the last also used conditional ref deletion. These observations do not establish a linearizability proof or identify the precise cause of GitHub’s generic rejection. This is evidence for a potential transport, not verification with an App token, protected branches, bypass rules, concurrent review or policy changes, or an ambiguous response. In particular, the generic error must not be classified as a definite rejection or blindly retried. `doctor` can inspect the GraphQL schema read-only; the presence of fields does not prove permissions or behavior. No GraphQL mutation is wired into Sluss.

On 2026-10-28, an additional experiment against Sluss PR #12 tested `refs/pull/12/head` as a no-op ref update alongside a temporary target update. GitHub rejected both matching and mismatched PR-ref requests during GraphQL input coercion: the PR ref was not accepted as `GitRefname`. An ordinary temporary branch update with the same base and candidate succeeded in the same run. The target and PR head remained unchanged during both PR-ref requests; both temporary branches were later observed absent. One deletion initially returned a stale ref read immediately after the mutation, but a later read showed it absent. This establishes the behavior observed for that repository and provider at that time, not the impossibility of every other API or configuration. GitHub separately documents that the [`refs/pull/` namespace is read-only for Git pushes](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally#error-failed-to-push-some-refs).

A later 2026-10-28 probe on the same PR observed that a no-op precondition on its actual source branch in the target repository was accepted: an absent or stale expected head left the temporary target unchanged, while the matching head allowed the target to advance and left the source branch and PR head unchanged. The test used a user credential and temporary unprotected target branches; it did not test an App, protected source branches or concurrent PR metadata, reviews or policy. Source branches in forks are outside the target repository's `updateRefs` transaction.

The experimental `freeze-landing-heads` command reads each PR, its source branch and synthetic pull ref twice with a scoped App token, requires the PR's source and target repositories to be the configured repository and each SHA to match the frozen batch, and binds the source refs and local delivery revision transactionally. Duplicate, unsafe, missing or changed refs and forks fail closed. Marker creation requires these guards first, and a marked experimental claim checks the frozen branches again; its GraphQL request contains a no-op expected-SHA update for each source branch. Once marker creation begins, the binding cannot be replaced; cancel and prepare another intent if inputs change. Older unguarded marker intents that already began creation cannot be upgraded in place. The source branch can still be deleted and recreated, and a PR's source mapping, reviews, labels and branch-policy state can change independently of its commit SHA. No provider write uses this request yet. These app paths have only been exercised against a stub.

Strict landing remains disabled until an end-to-end protocol establishes the full conditions under the actual App, repository, rules and concurrent actors; a source-branch guard, successful CI result, marker or target CAS cannot substitute for that proof. `doctor` reports this limitation.

An operator can repeat the bounded probe with `python3 scripts/probe-github-pull-guard.py --repo OWNER/REPO --pull <number> --base <sha> --candidate <descendant-sha>` (add `--guard branch` for a same-repository source branch). It creates two uniquely named temporary branches and includes the PR ref only as an unchanged before/after value, never as a new value. It conditionally deletes the temporary branches and waits for two 404 observations; forced termination, permission loss, delayed provider state or an unexpected ref change can leave cleanup unresolved. An inconclusive or rejected result is not permission to land. The probe may trigger repository workflows and has only been exercised with a user credential; it does not test App permissions, reviews, protected branches or forks.

The opt-in `scripts/probe-github-cas.py` repeats the concurrent ref experiment on an explicitly selected repository. It requires `gh` with a credential allowed to create, update and delete branches, and two distinct descendant commits already present in the repository:

```sh
python3 scripts/probe-github-cas.py --repo OWNER/REPO --base <base-sha> --first <descendant-sha> --second <other-descendant-sha>
```

The probe validates ancestry and creates five uniquely named temporary branches: one target, two staging refs and one marker per contender, each initialized to the base. It first submits an otherwise valid mutation with an incorrect marker precondition and verifies that all five refs remain unchanged. It then sends two competing mutations, each atomically comparing and updating its target and marker while checking its staging ref. It reads all refs and deletes each with an expected-old-SHA condition only when its observed SHA is expected. It verifies deletion but cannot clean up after a forced termination, network loss or an unexpected ref change; inspect any named refs reported as unresolved. Ref creation may trigger repository workflows.

On 2026-10-28, two user-credential trials of the three-ref contender observed exactly one acknowledged winner, with its target and marker at its candidate and the losing marker at the base; each trial confirmed deletion of all five refs. The second also observed that a wrong marker precondition left all five refs unchanged. These are limited observations on unprotected branches. A protected, uniquely bound marker could be useful when investigating an ambiguous result, but a matching marker alone does not prove who updated it or when; safe recovery would also require exclusive marker ownership, immutable operation identity, trusted observations and an end-to-end protocol. Neither lost responses nor App permissions, protected-branch behavior or review and policy freshness were tested. No marker is used by Sluss landing. The seven offline probe safety tests use a fake provider and are run in CI.

The experimental library can freeze and create a marker reference as part of a trusted batch-bound landing plan. It derives the reserved `refs/heads/sluss/receipts/<operation-id>` name from a caller-supplied 32-character lowercase hexadecimal ID; the operator must generate that ID uniquely and protect the reference from other writers. The serialized plan and its GraphQL request bind that exact ref, base and staged SHA. The source-branch guards must be frozen before marker creation. A separately scoped Contents-write token may create it once using the GitHub ref API after the repository and local plan are rechecked. The durable creation state is committed before the POST; an ambiguous response remains unresolved across restarts and is never resent. The experimental batch-bound claim requires a directly confirmed creation response and checks twice that the marker still points at the frozen base. An unbound local intent with a marker cannot be claimed. After an uncertain landing claim, recovery reads the marker twice alongside target and staging refs and journals the observation; it does not acknowledge the request, unlock the target, or allow retry. Historical plans without a marker remain readable.

These creation and observation paths have been tested only against a local GitHub stub, not an actual App. The CLI exposes explicit preparation, one-shot creation, read-only inspection and cancellation of unclaimed intents; the service does not create markers automatically and no path sends a landing mutation. An observed marker is not proof of request origin; secure ref ownership, App permissions, protected-branch behavior, review/policy races and lost-response recovery remain unverified. A marker-creation send whose response was lost cannot currently be resolved automatically, even when a matching ref is observed. `observe-marker-creation` reads the repository identity and marker twice using a scoped read token, then journals the historical result only if the local intent and creation state remain unchanged. A matching SHA cannot prove the original request succeeded; two 404 responses mean only that the marker is not visible to that token. Neither result changes creation state, sends a retry, unlocks a landing or proves merge eligibility. Observations remain accessible after cancelling the unclaimed intent.

`start-staged-check` is an opt-in experimental App path for a nonpassing `in_progress` check named `sluss/verified` on the exact staging SHA. The App repeats the CI candidate provider scan, then atomically rechecks its policy, candidate pointer, frozen run and delivery revision while journaling a single send before the Checks API POST. It uses a separate Checks-write installation token and validates the direct response against the issuing App, check and suite IDs, staged SHA, batch, in-progress status, absent conclusion and frozen output. An ambiguous response remains `sending` and is never retried automatically. `recover-staged-check` independently reads an operator-supplied check twice and records a recovered receipt without assuming request origin; a later inconsistent direct receipt is retained as a conflict. Check IDs cannot be shared with failure or other pending-check intents. An event after the send claim may invalidate the local candidate while the external check is being created: the check stays nonpassing and the historical receipt is still recorded. `staged-check` inspects the journal and current local candidate match read-only; it does not refresh provider state. The manual `cancel-stale-staged-check` requires a directly confirmed check and a stale local candidate pointer. It reads the exact check and issuing App twice, then rechecks the candidate and delivery revision in the transaction that claims one [Checks API update](https://docs.github.com/en/rest/checks/runs#update-a-check-run) to `completed`/`cancelled`. An event already acknowledged during those reads invalidates the claim. A lost or malformed response remains uncertain and is never resent; `recover-cancelled-staged-check` reads the known ID twice and records the observation without proving request origin. A late matching direct receipt is retained alongside recovery. A cancellation is terminal for that batch, including when a later event races with the external update. `staged-check` also displays this journal. The opt-in `serve --cancel-stale-checks` worker periodically finds direct stale checks and unresolved cancellation sends for the bound repository. It uses the same one-shot cancellation path and read-only recovery, and never starts a cancellation for a recovered-only or conflicted creation receipt. A previously sent cancellation can still be observed for its known check if a later creation receipt conflicts. It never retries an ambiguous update. No positive check, conflict resolution, live App validation or merge authorization is provided by this flow.

The explicit experimental `report-failed-check` command can publish only a `failure` check for an exact staging SHA after a direct, recorded failed run is reread. A repository-scoped Checks-write token is separate from the read token. The journal freezes the local CI observation, claims a single send before the POST, and records a receipt only when the returned App, check and suite IDs, SHA, batch ID and failure conclusion match. Ambiguous responses remain in `sending`; neither restart nor a concurrent caller resends them. HTTP client automatic retries are disabled. This operation is not a trusted CI attestation, never emits success, does not update the target, and has only been exercised against a local stub. It currently requires the batch to remain in `Testing` and the dispatch reservation to remain present.

The operator may supply a candidate check ID to `recover-failed-check`. Sluss reads the candidate twice and verifies its issuing App, repository, exact SHA, batch, failed conclusion and expected output against the frozen record. Recovery uses read access, never repeats the write and can associate a historical failure even after a batch is stale. The source is recorded as recovered: matching metadata cannot prove which request created the check. If a later direct response identifies a different check, the disagreement is recorded durably as a conflict. The resulting record is not trusted CI evidence and cannot authorize landing. Discovery of candidates and live-provider recovery remain unverified.

The experimental batch-bound landing claim also reads GitHub's GraphQL `reviewDecision` for each member, both before and after the CI snapshot, with two matching reads each time. It requires `APPROVED`, an open non-draft PR, the frozen head and base, and the expected repository node and target branch; null, errors, unknown decisions and changes fail closed. GitHub describes this field as the current review status, not as an atomic proof of all branch rules or CODEOWNERS requirements. These observations are an additional rejection gate only: GitHub can change them after the reads, and they neither authorize a ref update nor replace policy validation. The query has been exercised with a user credential against a real PR and with an App-token stub; actual App access and policy behavior need live validation.

The experimental `local_refs::compare_and_advance` library function exercises a smaller Git mechanism in a trusted local SHA-1 bare repository. It verifies the staging SHA and the expected old target while holding both ref locks, refuses symbolic refs, checks commit ancestry, and advances to the exact staging commit using Git's [reference transaction](https://git-scm.com/docs/git-update-ref). It is not connected to the service, CLI or GitHub, and does not check reviews, CI, policy or authorization. Its caller must control the Git executable, repository configuration, object database, filesystem and ref writers. The checks cover values while locks are held, not an ABA change, a concurrent policy or review change, or a later writer. It has no durable write journal: an uncertain outcome must not be treated as success or automatically retried, and a forcibly terminated Git process can leave locks that require careful reconciliation. A local transaction does not establish a GitHub compare-and-swap capability.

The separate experimental `LandingJournal` records a frozen prospective GraphQL operation in SQLite WAL with full synchronization. It serializes unresolved intents per repository and target within the same database, returns the immutable plan to the one worker that claims it, and does not allow a claimed intent to be cancelled or reclaimed after restart. The generated request compares both the frozen target and staging refs with `force: false`. A trusted transport may record a matching successful direct response and its digest; errors, partial responses, lost responses and later readback are not acknowledgements. `clientMutationId` correlates a response and is not an idempotency key. There is currently no mechanism to resolve an uncertain intent, and separate databases or unmanaged writers are not serialized. The read-only provider operation `observe-landing-recovery` validates the scoped installation, repository ID and node ID, then reads the frozen target and staging refs twice with the App read token. Stable commit ref observations are recorded with the complete frozen plan and a digest in the local journal only if the same intent is still `sending`. The observation distinguishes the base, staged and another target SHA and records a moved staging ref; missing refs, changed reads or an acknowledgement racing the scan leave no new observation. `landing-recovery` opens an existing database read-only and displays the latest historical record after restart; it does not create or migrate the database. Neither observation nor local digest proves request origin, current ref state, branch authorization or successful landing; it never acknowledges, unlocks or retries an intent. This path has only been tested with a local stub. The journal neither sends requests nor establishes the authenticity of its input digests, Git ancestry, fresh admission, branch policy or CI evidence. The service and CLI cannot send a landing update, and these observations cannot authorize a merge. A production integration must atomically bind publication to current trusted batch evidence and define safe reconciliation before enabling landing.

An experimental batch-bound journal path derives its admission and CI digests from the same database transaction as preparation. It requires the current local base and heads, frozen review evidence, no pause or pending reconciliation, the frozen workflow path, a direct dispatch receipt and a complete successful recorded CI snapshot with no conflict marker. Claiming repeats those checks and compares the entire resulting plan in a write transaction; the unbound claim API refuses a batch-bound intent. These checks only bind previously observed data. They do not verify the repository node ID, provider freshness, trusted workflow contents, review or policy races, or anything that changes after the claim. No journal path is connected to a provider write.

A separate experimental App helper refreshes each included PR, reviews and reviewer permissions against the frozen admission evidence and operator policy. It reads the target and staging refs around the scan, refreshes the first Actions attempt and complete job list twice, reads the latest run around those observations, and checks the installation's numeric repository ID and GraphQL node ID. The resulting provider snapshot is compared with the frozen CI record inside the claim transaction. Changed inputs, a rerun, an incomplete or different run, or pending local reconciliation stop that claim. These reads are not an atomic GitHub snapshot: a later push, rerun, revoked review or policy change can still occur, so this is not trusted CI attestation or landing authorization. The lower-level local-only claim remains available for development and must not be used as a provider freshness check. This helper has only been tested against a local GitHub stub and is not connected to a GitHub write or the service.

For a completed CI observation, every observed job must be complete and have a conclusion, even when it is not a required job. A skipped optional job may remain in the snapshot. Contradictory terminal run and unfinished job states are rejected rather than saved as evidence; saved snapshots are revalidated before CI-only completion or bisection comparisons after an upgrade. This does not validate workflow semantics or the completeness of the operator policy.

The separate CI-only `verify-staged-ci` flow compares the current App-observed repository, both refs, PRs and reviews, branch-security snapshots, exact first-attempt Actions run and complete jobs against a frozen batch and operator-owned `TrustedCiPolicy`. It checks the authenticated App identity around the scan, then rechecks the local queue and snapshot in a single write transaction and stores a content-addressed candidate. It does not require a branch-rule bypass, send a GitHub check or claim a landing intent. The candidate can be recorded while CI is testing, after successful CI-only completion, or after bounded runner release; the completed run ID, direct receipt, terminal reservation state and immutable CI observation must still agree. Changed heads or reviews, a queued webhook, CI or receipt conflicts, wrong policy, altered refs, reruns or changed snapshots fail closed. Repeated scans of the same content reuse the immutable record and atomically point to the most recently reverified candidate for that policy, including when older content returns. `inspect-staged-ci` opens the database read-only and compares that record against current local state; it does not refresh GitHub. Every new scoped provider delivery clears current candidate pointers in its delivery transaction; duplicate or foreign deliveries do not. A distinct signed payload or event reusing a delivery ID is journaled as a collision and schedules reconciliation rather than being discarded; the endpoint still reports conflict. Repeated identical collisions are deduplicated, and a security collision invalidates active work in the same transaction. Immutable history remains. A changed base, head or admission observation during periodic reconciliation and a selection-policy migration also clear the pointers. Provider scans and experimental fresh landing claims compare the durable AUTOINCREMENT delivery revision before and after network reads, rejecting even an event or internal scan already acknowledged before the read completes. The currently bound selection mode must match the frozen dispatch. Periodic scans without a relevant change do not themselves erase saved candidates. These checks cannot detect provider changes that are never delivered or observed, and they do not make provider reads atomic with later changes; the digest is not a signature. Operator control of the full policy dependencies and runner isolation remains an assumption; the record is not a trusted attestation or authorization to merge. These paths are tested only with a local provider stub.

The App helper now requires an independently supplied `TrustedCiPolicy` to be frozen atomically with the batch-bound intent using `prepare_trusted_batch`. Its canonical digest binds installation, repository and target, repository admission policy, the staged policy-file digest, workflow ID and path, exact required job names, suite selection policy and names, and allowed runner IDs. The intent itself also stores the digest; preparation, claim and acknowledgement require the separate policy binding and that digest to agree. Supplying a changed policy, omitting the binding, modifying its stored digest, or using the unbound local claim for a trust-bound intent fails closed. Trust-bound preview intents created before the digest was included in the plan are refused: cancel and recreate an unstarted intent, while a claimed intent remains uncertain. The policy is a caller-supplied trust anchor: equality cannot prove that all workflow dependencies were included, external actions were pinned, the workflow actually tests what it claims, or a runner is isolated. The caller must obtain and protect the manifest outside PR control. No CLI or service currently loads this policy for landing, and no positive check or ref write is enabled by it.

For local review, `policy-digest` hashes an explicit list of regular files at a full commit SHA in an operator-trusted local Git repository using the same encoding as staging. It reads committed objects, not the working tree; it does not authenticate the commit or ensure the list is complete. `inspect-ci-policy` loads a bounded TOML policy and opens the database read-only to compare it with an already recorded batch; it neither creates an intent nor contacts GitHub. `ci-evidence` displays the recorded admission-policy digest, job and suite values to help investigate differences, not to endorse those values. A matching inspection does not validate the policy's contents, refresh provider state or authorize a merge. The serving and landing paths do not yet load this file.

`preview-trusted-batch` uses the same read-only local comparison and the experimental App provider-refresh path, without preparing or claiming a landing intent. It requires the configured App identity, scoped repository, visible branch security, frozen refs, current PR admission and provider review status, and the recorded first-attempt CI snapshot to agree. After the network reads it repeats the local database comparison, so pending reconciliation or a changed batch stops the preview. The database is opened read-only; separate short-lived App tokens are minted for reading and administration. The reads are not atomic with one another or with GitHub state after the command returns. They do not verify workflow semantics, runner isolation or CODEOWNERS and do not issue an attestation, check or merge approval. This command is stub-tested only and does not establish that a real App has the necessary permissions.

A run's reported workflow path is compared with the workflow file frozen at dispatch. If GitHub includes an `@ref` suffix, Sluss now accepts it only when it names the frozen staging branch (fully qualified or short) or the exact integration SHA. A different branch, tag, commit or malformed suffix rejects the observation, including in dispatch recovery, cancellation, capacity release, landing candidates and CI-only completion. Old stored snapshots are checked again before CI-only completion or use in bisection; previously completed records are not retroactively rewritten. GitHub's [workflow-run API](https://docs.github.com/en/rest/actions/workflow-runs) also permits path responses without a suffix; those provide no independent evidence of the ref, so Sluss separately checks the run's SHA and branch. These comparisons are not proof of workflow semantics. The accepted suffix formats and their behavior have only been tested with a local stub, not a real App dispatch; a different GitHub response will fail closed and may leave the reservation for operator recovery.

GitHub requires a workflow file to exist on the repository's default branch for `workflow_dispatch` to trigger ([GitHub events documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)). An active workflow registration alone does not prove this: on 2026-10-28 the Sluss repository reported its CI workflow active while the file was absent on `main`. Before claiming any dispatch, Sluss reads the current default branch and traverses its immutable Git trees to find the exact registered path as a regular file; missing files, symlinks, duplicate entries, truncated responses, inconsistent identities or changed branch state stop the send. It rechecks the registration and default-branch head before claiming. `doctor` performs the same presence check. A prepared capacity reservation remains held until cancelled or successfully dispatched. Sluss also fetches the exact content-addressed workflow blobs from the default and staged commits, validates the Git blob IDs and uses a bounded YAML parser to require an explicit `workflow_dispatch` mapping with string-typed `sluss_host` and `sluss_suites` inputs before the send. Any additional input must not be required. `doctor` checks the default and selected target commit. Scalar and list trigger forms cannot declare the required input mappings and do not pass this Sluss-specific check. The opt-in adaptive CI-only controller is bound to the planning settings and requires one active batch. After any reduction, six full successes are required before another increase. A contradictory CI receipt marks its sample invalid and resets the active limit to one.
