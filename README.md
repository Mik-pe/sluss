# Sluss

Sluss is intended to be a small, open-source CI orchestrator and merge queue for repositories with limited build capacity.

> Run CI for the code you're actually going to merge. Batch the work, not the risk.

## Status: early development

The current development preview contains a durable SQLite queue, batch state machine, physical-host reservations, a Git integration builder, authenticated GitHub App reconciliation, and optional workers for planning, staging, dispatch and observation. These paths have not been validated end-to-end against a real GitHub App and runner. The service and CLI do not establish trusted CI attestation or update target branches, and the project is not ready for production or a pilot. A `Verified` state is not merge authorization; the strict `doctor` exits unsuccessfully until the required checks exist. The writable SQLite connections require WAL and `synchronous=FULL`; they fail if WAL cannot be enabled. Use a filesystem that supports SQLite WAL and preserves sync semantics. Power-loss behavior has not been tested on a target deployment.

The experimental landing journal can freeze and create a per-operation receipt ref, then record its observed SHA after an uncertain landing. Creation uses a separately scoped App token and a durable one-shot journal; an ambiguous result is not retried. These App paths are tested with a stub only. Sluss does not send a landing mutation, resolve uncertain sends or authorize a merge based on the marker. See the [protocol](docs/protocol.md).

Operators experimenting with a recorded successful batch and a separately reviewed trusted policy can use:

```sh
sluss --db sluss.sqlite prepare-landing-marker --batch-id <batch-id> --policy /path/to/trusted-ci-policy.toml
sluss --db sluss.sqlite landing-intents
sluss --db sluss.sqlite freeze-landing-heads --operation-id <id> --config /path/to/sluss.toml --policy /path/to/trusted-ci-policy.toml
sluss --db sluss.sqlite create-landing-marker --operation-id <id> --config /path/to/sluss.toml --policy /path/to/trusted-ci-policy.toml
sluss --db sluss.sqlite observe-marker-creation --operation-id <id> --config /path/to/sluss.toml
sluss --db sluss.sqlite landing-recovery --operation-id <id>
```

Preparation generates and prints a random ID; `landing-intents` recovers it if output is lost. Freeze each PR's same-repository head branch before creating the marker; forks are rejected. An older marked intent whose marker was already created without head guards must be cancelled and prepared again. Creation makes a GitHub branch and may trigger workflows. Configure `SLUSS_GITHUB_PRIVATE_KEY_PATH` and protect the reserved marker namespace from other writers. If creation remains uncertain, the attempt will not be resent or automatically resolved. The observation command reads twice and records a historical snapshot; a matching SHA does not prove who created the ref, and a 404 means only that the ref is not visible to the token. `cancel-landing --operation-id <id>` releases only an unclaimed landing intent; a marker creation may still have succeeded and requires inspection or cleanup. These commands do not enable automatic landing.

Strict landing is not enabled: experimental no-op guards cover only frozen source branches in the same repository, and cannot atomically guard PR metadata, reviews or branch policy. A provider probe found that GitHub rejected a PR's synthetic `refs/pull/.../head` as a GraphQL ref-update input. See the [protocol](docs/protocol.md) for the evidence and its limits.

For an experimental installation, `sluss app-registration-url --name "My Sluss Preview"` creates a GitHub registration link with read-only permissions and webhooks disabled. It does not create an App. See [GitHub App setup](docs/github-app-setup.md) for the separately opted-in CI permissions, webhook setup and key isolation.

It requires the App's Checks-write permission, rereads the run and never publishes success. An ambiguous send is not retried. Both commands have only been tested against a local GitHub stub and neither provides trusted attestation or merge approval.

Before a GitHub staging push, Sluss examines every direct `.yml` or `.yaml` workflow in the integration commit and refuses publication if it sees a `create` trigger or cannot rule out a `push` trigger on that exact `sluss/` branch. A `branches` list whose patterns have a clearly different literal prefix, or `branches-ignore: ["sluss/**"]`, can establish that exclusion; ambiguous YAML, unsupported patterns, symlinks and oversized files fail closed. This check also covers workflow files added by a PR. If the frozen base is safe but the batch introduces an unsafe or ambiguous workflow, Sluss fails and splits the batch; an unsafe singleton is held for review. An unsafe base or an inspection failure remains an operator error and does not blame a PR. It does not cover `workflow_run`, other event types, external automation or organization runners; operators must control those separately. Which workflow version GitHub evaluates for every creation scenario has not been verified with a live App. Local staging does not enforce this GitHub-specific check. See [integration details](docs/integration.md).

To try webhook intake locally, set `SLUSS_WEBHOOK_SECRET` in the environment and run `cargo run -- serve`. It listens on `127.0.0.1:8080` by default; `--listen` changes the address. External traffic requires a trusted HTTPS reverse proxy. Without configuration, this only records deliveries.

With a configured installation and repository, well-formed `check_run`, `check_suite` and `workflow_run` hints invalidate saved CI candidates without restarting an in-flight PR admission scan. A newly recorded matching hint can wake the CI observer in the same process after a debounce of at least five seconds; the observer reads GitHub rather than trusting the payload. It scans at startup and retains at least a 60-second fallback poll, while failed reads back off. Duplicate and conflicting deliveries do not send a wakeup, and another process sharing the database relies on its own polling. Ambiguous bodies, delivery-ID collisions, PR and security hints, and unscoped receivers retain a full reconciliation wakeup. Missed PR events may delay queue changes until the next periodic scan.

With a configured installation and repository, security-related webhook hints also invalidate active batch evidence and old CI-only holds before scheduling reconciliation. Installation-wide and organization ruleset events without a repository are routed conservatively to that configured repository. Already running jobs and reservations still need cancellation and recovery. Membership and team events depend on GitHub App subscriptions and permissions; delayed or missing events mean fresh checks remain necessary.

On a fresh database, planning, CI observation, rerun accounting, bounded release, stale-run cancellation and stale-check cancellation wait at the configured poll interval until the first repository reconciliation binds the queue; they do not treat that expected startup state as a provider failure. Actual database, policy and scope errors still fail closed. A successful automatic dispatch wakes the local observer after its usual debounce even if webhooks are disabled; uncertain sends are not retried.

Before starting workers, `serve` validates the configured capacity, dispatch request, policy paths and selective policy. It also opens the scheduler before launching workers, refusing a capacity change that conflicts with an existing reservation or frozen release topology. A compatible topology can be bound or updated at startup under the scheduler's existing rules. These checks do not establish runner availability or provider permissions; later concurrent changes are still checked by individual operations.

Review comments and pending reviews do not invalidate a batch when the actual decisions are unchanged. Stop older Sluss workers before upgrading: the new admission digest will invalidate old frozen review evidence on reconciliation and can require CI to run again.

Add `--auto-plan` to the configured service to create batches automatically from its reconciled queue. The queue configuration controls maximum batch size, concurrent active batches, debounce and collection window; see [the example](examples/sluss.toml). The first automatic planning pass binds these settings to the database, and conflicting manual or automatic planners fail closed. Changing bound settings requires the explicit paused migration described below. `sluss status` shows active batch IDs and states after restart. With planning alone, batches stop at `Planned`; no batch authorizes a merge.

An optional CI-only controller can adapt the ordinary batch limit: set `adaptive_batching = true` under `[queue]`, keep `max_active_batches = 1`, and enable `--auto-plan --observe-dispatches --complete-ci-only` with the required capacity settings. `max_batch_size` remains the hard maximum. The controller starts at two (or the configured maximum if smaller). Three consecutive full-size, successful, directly observed runs with measured runner time allow a one-step increase. When at least three comparable root batches exist at each adjacent size, it compares a conservative cost index over the latest six: runner time from successful and failed root runs plus observed bisect jobs, divided only by candidates in successful root batches. If that index is over 10% higher at the larger size, it lowers the limit; it will not return to a previously measured, more expensive size while the comparison remains valid. A failed multi-PR batch reduces the limit to at most half its size, even if its timing is unavailable. A reduction requires six further full successes before exploring a larger size again. Different workflow/policy/runner identities do not share streaks or cost baselines; missing timings and other conclusions break the success streak; an untimed success in the latest six blocks a cost comparison, and bisected children contribute measured investigation time without contributing a success streak or delivered-PR count. An unfinished, stale or unmeasurable investigation blocks expansion to the affected size. A later contradictory CI observation invalidates its sample and resets the limit to one. `sluss status` shows the limit and sample count; `sluss adaptive-history` lists recent decisions without modifying the database. Existing installations must use the drained `migrate-planning` procedure below to change this option; a configuration change starts a new sample epoch. This opt-in heuristic can perform exploratory builds and does not account for later reruns, unobserved work, delivered PRs or changing workloads. Its denominator deliberately excludes passing bisected groups, so the index is not runner-minutes per merged PR. It has not shown a pilot saving, does not identify a failing PR, and never authorizes a merge.

To adjust batch size, active-batch limit, debounce or collection window, drain active batches and reservations, stop Sluss workers and external staging/dispatch processes, then run `sluss pause`. Copy the planning digest shown by `sluss status` (or `unbound` if no planner has bound settings). Edit the operator-owned configuration and run `sluss migrate-planning --expected-digest <digest> --config /path/to/sluss.toml`; restart workers with that configuration and run `sluss resume`. The transaction requires the same installation, repository and target, a paused and drained queue, no unresolved dispatches, and an unchanged digest. It retains queue entries, CI-only holds, investigation history and pending split tasks; if a pending split is larger than the new maximum, the migration refuses it rather than dropping or reshaping that work. Complete or reconcile those splits with the old settings before retrying. Existing workers must be stopped because local state cannot prove that external processes have exited. This is manual tuning, not automatic optimization or a claim that the new batch size saves runner time.

The `--release-ci-only` worker can perform this check automatically. Sluss rechecks both run identities, attempts, workflow paths, completed jobs, runner placement and idle repository inventory; overlapping run ownership fails closed. A historical observation record and the release commit atomically. The original conflict remains invalidated: this does not prove which request created a run, attest CI or authorize a merge. These paths have only been tested against a local stub.

For CI-only scheduling, add `--complete-ci-only` alongside `--observe-dispatches`. After a directly received run has a completed first-attempt provider observation, Sluss retires the scheduling batch and holds its unchanged PR heads until their inputs change; this holds for both successful and failed outcomes and does not grant merge approval or classify a failure as a bad PR. `sluss retry-ci --batch-id <id>` clears those holds. Runner reservations remain held unless the separate conservative release option is enabled. Recovered or legacy-unknown run IDs are observed but are not completed automatically.

To investigate failed CI-only batches, add `--bisect-ci-failures` with `--complete-ci-only --observe-dispatches` and enable the planner, staging and dispatch workers needed to run the resulting halves. Sluss tests both halves and only continues into a failing half when its sibling succeeded with comparable frozen inputs and CI policy. Both failures, both successes, different policies or suites, and non-failure conclusions stop the investigation as inconclusive. Changed inputs make it stale. A failing singleton is marked for review, not identified as guilty; infrastructure failures and interactions between changes remain possible. Split batches use the full configured suite list so their results can be compared. This is scheduling assistance, not merge approval or trusted attestation. The first CI-only worker binds this option in the database. To change it, stop all Sluss workers and external staging or dispatch processes, allow active batches and CI investigations to finish, reconcile and release reservations, and run `sluss pause`. Copy the CI bisection revision from `sluss status`, then run `sluss migrate-ci-bisection --expected-revision <revision> --config /path/to/sluss.toml --enable` (or `--disable`). Restart all workers consistently and run `sluss resume`. The transaction checks the bound repository and target, requires a paused and drained queue with no unresolved dispatches or unfinished investigations, preserves investigation history and CI holds, and rejects stale revisions. SQLite cannot verify that external workers have stopped; the operator must do so before migration.

For an experimental bounded CI-only release, add `--release-ci-only` with `--complete-ci-only --observe-dispatches`. A successful observation pass sends a coalesced in-process hint to the release worker, which retries after at least five seconds rather than waiting for its next minute poll. The hint is advisory: startup and periodic scans recover lost or cross-process signals, and failed revalidation retains its backoff. It rechecks the exact completed run, observed placement and the complete repository runner inventory before releasing its reservation. The reserved host must be idle and online. If it is busy, ordinary release leaves that reservation in place and checks later completed batches; an incomplete or inconsistent inventory still stops the pass. Conflict resolution still requires all configured hosts idle. It can also release a directly identified run belonging to an invalidated batch once that run is completed; completed jobs on the confirmed runner are counted in metrics, while a run cancelled before any job starts may have no placement. Unknown or solely operator-recovered run identities remain reserved; a documented conflict has a separate bounded recovery path. This mode requires exactly one configured runner and one slot per physical host, and each global pool budget must cover the sum of that pool's host capacities. GitHub runs only one job at a time per runner, so this conservative envelope reserves enough pool capacity even if an old workflow is rerun. The operator must ensure each host has no additional runner process, all work on that host stays within its declared pool capacities, no untracked workloads use the same global pools, and completed jobs cannot leave work running; GitHub inventory cannot verify physical colocation, other runner scopes or process cleanup. The first bounded release binds the topology. To expand it, stop all Sluss and manual staging/dispatch workers, drain active batches and reservations, run `sluss pause`, and copy the capacity digest from `sluss status`. Then run `sluss migrate-capacity --expected-digest <digest> --config /path/to/sluss.toml --capacity /path/to/new-capacity.toml`, restart workers with the new file and run `sluss resume`. The transaction requires the bound repository and target, a paused and drained queue and unchanged digest. After a bounded release it allows only an expanded single-runner envelope: every old host, runner ID and pool allocation must remain, and budgets cannot decrease. Old conflict-release records retain their original topology. Removing or replacing runners and reducing capacity require a future protocol for old reruns. Stopping workers and the physical isolation assumptions remain operator responsibilities. This has only been tested against a local provider stub, not real runners, and it does not authorize landing.

The expected GitHub job names are frozen in each dispatch. `observe-dispatch` compares the provider result with those names, the exact run and commit, the reserved host and the current batch. A completed run is rejected as contradictory unless every observed job, including optional jobs, is completed with a conclusion; skipped optional jobs remain allowed. Sluss stores the observed run and normalized job records for completed comparisons; `sluss ci-evidence --batch-id <id>` displays them and any persistent conflict. A reported workflow-path suffix must match the frozen staging branch or exact integration SHA; an incompatible or unfamiliar suffix stops observation and may leave capacity reserved for recovery. A path without a suffix does not independently prove workflow provenance. A later contradictory snapshot blocks CI-only completion and capacity release; older summaries without a job snapshot are retained without inventing missing details. These records do not issue `sluss/verified` or authorize a merge. Trusted workflow policy and branch protections are not yet established.

For experimental CI evidence collection, `sluss verify-staged-ci --batch-id <id> --config /path/to/sluss.toml --policy /path/to/trusted-ci.toml` compares the exact recorded Actions run and jobs with fresh App-observed repository, refs, reviews and branch-security snapshots and an independently controlled [CI policy](examples/trusted-ci-policy.toml). It records a content-addressed candidate only if the local batch, admission and policy still agree after the provider reads. The same observation can be recorded after a successful CI-only completion and bounded runner release. This CI-only operation does not require the App to bypass branch rules, but it does require complete branch-security snapshots; unavailable details fail closed. `sluss inspect-staged-ci --batch-id <id> --policy /path/to/trusted-ci.toml` reads the saved record and rechecks local state without querying GitHub or creating a database. A new scoped webhook or a distinct conflicting delivery clears the current candidate pointer while retaining its historical record; reconciliation changes to candidates or the target and selection-policy migration also clear it. A monotonically increasing delivery revision makes scans fail if an event or periodic reconciliation starts and finishes while GitHub is being read. The saved digest detects accidental changes, not malicious database writes; provider state can change after observation or without a delivered event. The operator must protect the policy, include all workflow dependencies and isolate runners. Neither command publishes `sluss/verified`, establishes a trusted attestation or authorizes landing.

For an experimental, nonpassing GitHub check on the staging commit, `sluss start-staged-check --batch-id <id> --config /path/to/sluss.toml --policy /path/to/trusted-ci-policy.toml` first refreshes the CI candidate and journals a single send before using a separately scoped Checks-write App token. It creates `sluss/verified` with status `in_progress` and no conclusion; it never issues a success or authorizes a merge. If the response is lost, inspect `sluss staged-check --batch-id <id>` for the receipt and current local evidence match, and use `sluss recover-staged-check --batch-id <id> --check-id <id> --config /path/to/sluss.toml` only after identifying the candidate on GitHub. Recovery verifies the App, repository, check and suite identity, exact staging SHA and frozen summary; matching metadata does not prove request origin. Sluss never blindly resends an uncertain request, and records contradictory receipts as a conflict. The journal is inspectable after restart. When local evidence is stale, `sluss cancel-stale-staged-check --batch-id <id> --config /path/to/sluss.toml` can cancel a check that was directly confirmed by the App; it rechecks the issuing App and check identity twice and journals at most one update. If the response is uncertain, `sluss recover-cancelled-staged-check --batch-id <id> --config /path/to/sluss.toml` observes the known check without resending; recovery does not prove request origin. Cancellation is terminal for that batch. Add `--cancel-stale-checks` to `serve --config ...` to run this path automatically and read back uncertain cancellations; the worker checks repository scope, requests Checks-write separately, and does not resend an uncertain update. An event after the local claim can race with the external update; the result stays nonpassing. Check receipt conflict resolution remains unimplemented. This path is opt-in, has only been tested against a local stub, and must not be used as merge evidence.

`sluss metrics` sums actual start-to-finish time for completed, host-checked jobs observed by Sluss. Repeated reads of the same job do not double count it. It also reports completed scheduling-delay intervals grouped by requested pool: from the first failed capacity observation to a later eligible reservation, including polling gaps, pauses or outages. A request for multiple pools appears under each pool; this is not proof that any specific pool was saturated and must not be summed as runner time. Incomplete intervals and requests never attempted by the scheduler are excluded. Both measures use partial observations; jobs Sluss has not observed and unverified placement are excluded, and per-PR savings are not reported. To include a completed rerun, use `sluss collect-rerun-metrics --batch-id <id> --attempt <n> --config /path/to/sluss.toml --capacity /path/to/capacity.toml`. Sluss double-reads that attempt and requires a directly acknowledged original run, the frozen workflow and commit, and an original job measurement anchoring the runner host. It records measured completed jobs idempotently and reports rerun totals separately. Use `--all-attempts` instead of `--attempt <n>` to discover the run's attempts, record completed ones and report those still running. Discovery is bounded to 100 attempts and 10,000 jobs, and rejects a changed run during collection. Each attempt commits separately, so a failed pass can leave earlier measurements saved; repeating it is idempotent. Add `--observe-reruns --capacity /path/to/capacity.toml` to the configured service to collect them periodically. It scans at most four directly acknowledged batches per pass, at intervals of at least 60 seconds, with a durable round-robin cursor and completed-attempt checkpoint. A restart may postpone an interrupted batch until the next sweep; missing original measurements, recovered or conflicting receipts and provider omissions are excluded. Per-run scan errors persist and appear in `sluss rerun-status` and the error count in `sluss metrics`; a later successful automatic scan clears them. Manual collection does not clear the automatic worker's issue. No recorded errors do not prove completeness. The scan remains partial, makes GitHub API requests and never releases capacity or authorizes a merge. The path has only been tested against a local GitHub stub.

Optional delivery accounting is enabled with `serve --config /path/to/sluss.toml --observe-deliveries`. It scans at most four formerly admitted PRs per pass, at intervals of at least one minute, and requires two matching GitHub reads before recording a merge to the configured target. Two slots prefer the newest ended admission episodes that have not yet been claimed; the other two advance the historical cursor. If no new episodes are available, all slots can advance the cursor. A claim is saved before the provider read, so a crash or failed read can defer its retry to the historical sweep. Only PRs observed locally as admitted before GitHub’s merge timestamp can be counted. A durable cursor and scan claims make retries idempotent and reject observations overtaken by local events; conflicting later observations exclude the record and increment the conflict count. Missing or inaccessible PRs are skipped, and saved records are point-in-time observations. The count is incomplete: it excludes PRs Sluss never observed as ready and can lag by a full sweep. Local and provider clock differences can affect eligibility. `sluss metrics` separately shows the number, median and p90 of matched local admission-to-merge samples. These use GitHub’s currently returned head and local observation times, not an exact ready time, proof of continuous eligibility, or an association between the merge and a CI run. No savings ratio is inferred. This worker has been tested against a local provider stub, not a live GitHub App.


`sluss collect-benchmark --config /path/to/sluss.toml --request /path/to/selection.json` fetches selected GitHub run attempts, measured job times and merged PRs into benchmark JSON without creating a database. To retain a pilot’s observed admission times, Sluss records local eligible observations from reconciliations, including separate episodes for changed heads, evidence or base; inspect them with `sluss admission-history --pr <number>`. Add `--admission-db /path/to/sluss.sqlite` to collection to match eligible Sluss-cohort deliveries by current GitHub PR head and bound repository policy. The report labels these separately as observed admission-to-merge, not exact ready-to-main latency; missed events, later provider changes and local clock problems limit the result. Its selection and both completeness flags remain operator-reviewed; omitted jobs are listed on stderr, and it does not infer PR-to-run links or exact ready times. It has only been tested against a local GitHub stub. See the [selection example](examples/benchmark-selection.json). `sluss benchmark --input examples/benchmark.json` demonstrates a separate before/after report using **synthetic data**. For a real pilot, operators must collect complete job attempts and delivered PRs independently and describe the cohort boundaries and omissions. The command reports runner time per delivery, reruns, optional run-to-PR associations and ready-to-merge samples; it does not validate the source data or prove savings. See [pilot measurement](docs/benchmark.md).

The database defaults to `sluss.sqlite` in the current directory; use `--db PATH` to select another. The pause flag and observations survive restarts; pause also stops the experimental batch planner. Queue entries must eventually be reconciled against GitHub; an observation is never an approval.

## Intended operation

* **CI-only:** schedule existing workflows without changing merge behavior. A batch result is not a per-PR merge approval.
* **Strict merge:** build an integration on a frozen base and PR heads, verify that exact commit, recheck all authorization and policy, and update the target only if the update preserves the required invariants. No silent fallback to squash or ordinary GitHub merges.

Sluss must remain independent of any specific repository. See [architecture](docs/architecture.md), [protocol](docs/protocol.md), and [security](docs/security.md) for the design and open work.
