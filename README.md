# Sluss

Sluss is intended to be a small, open-source CI orchestrator and merge queue for repositories with limited build capacity.

> Run CI for the code you're actually going to merge. Batch the work, not the risk.

## Status: early development

The current development preview contains a durable SQLite queue, batch state machine, physical-host reservations, a Git integration builder, authenticated GitHub App reconciliation, and optional workers for planning, staging, dispatch and observation. These paths have not been validated end-to-end against a real GitHub App and runner. The service and CLI do not establish trusted CI attestation or update target branches, and the project is not ready for production or a pilot. A `Verified` state is not merge authorization; `doctor` exits unsuccessfully until the required checks exist.

For an experimental installation, `sluss app-registration-url --name "My Sluss Preview"` creates a GitHub registration link with read-only permissions and webhooks disabled. It does not create an App. See [GitHub App setup](docs/github-app-setup.md) for the separately opted-in CI permissions, webhook setup and key isolation.

For a currently testing batch with a directly recorded failed CI run, the explicit experimental `sluss --db sluss.sqlite report-failed-check --batch-id <id> --config /path/to/sluss.toml --capacity /path/to/capacity.toml` can create a **failure-only** `sluss/verified` check on the staging commit. It requires the App's Checks-write permission, rereads the run and never publishes success. An ambiguous send is not retried. An operator can supply a candidate ID to `sluss --db sluss.sqlite recover-failed-check --batch-id <id> --check-run-id <id> --config /path/to/sluss.toml --capacity /path/to/capacity.toml`; matching metadata does not prove the original request created it. Both commands have only been tested against a local GitHub stub and neither provides trusted attestation or merge approval.

An experimental library function can advance a branch in a trusted **local bare Git repository** using a reference transaction. It is not connected to the service or CLI, does not provide authorization, and is not GitHub landing. See the [protocol](docs/protocol.md) for its assumptions and limitations.

An independent experimental landing journal can freeze a prospective GitHub ref update and retain uncertain attempts across process restarts. It does not send requests, authenticate evidence, or authorize landing; recovery of an uncertain attempt is not implemented.

Its batch-bound claim also requires repeated, matching `APPROVED` review decisions from GitHub for each frozen PR. This is an additional transient rejection check, not proof of branch policy or CODEOWNERS compliance; the App-token path has only been tested against a local stub.

The App claim additionally requires an operator-supplied `TrustedCiPolicy` frozen with the batch, covering the workflow and policy digest, required jobs, suites and allowed runner IDs. This library-only prerequisite does not validate the policy's completeness or enable attestation and landing. See the [protocol](docs/protocol.md).

To compare a policy locally, independently review a trusted commit and list every policy dependency. Run `sluss policy-digest --source /path/to/trusted/repo --commit <full-sha> --policy-file .github/workflows/sluss-ci.yml`, repeating `--policy-file` for every dependency. Fill in an operator-owned policy based on [the example](examples/trusted-ci-policy.toml), then run `sluss --db sluss.sqlite inspect-ci-policy --batch-id <id> --policy /path/to/trusted-ci-policy.toml`. `sluss ci-evidence --batch-id <id>` displays the recorded job, suite and policy values for comparison; observations are not recommendations. These commands cannot establish that the policy list is complete, that a commit or runner is trustworthy, or that the provider state is current. They do not create an intent, issue an attestation or authorize a merge.

With an installed App, `SLUSS_GITHUB_PRIVATE_KEY_PATH` and repository configuration, `sluss --db sluss.sqlite preview-trusted-batch --batch-id <id> --config /path/to/sluss.toml --policy /path/to/trusted-ci-policy.toml` additionally compares the batch against fresh GitHub observations. It requires visible branch security consistent with the experimental strict-landing assessment, and rechecks local state after the network reads. The provider can change immediately afterward. This command creates no landing intent or check, is not an attestation or authorization, and has only been tested against a local GitHub stub.

```sh
cargo test
cargo run -- status
cargo run -- queue
cargo run -- metrics
cargo run -- pause
cargo run -- resume
cargo run -- doctor
```

`sluss doctor --config /path/to/sluss.toml --capacity /path/to/capacity.toml --workflow-id <id>` inspects the configured branch, active rules, visible ruleset bypass actors, classic branch protection, workflow registration, repository runner inventory, App token scopes and available GraphQL ref-update schema fields. It also checks the App's JWT-authenticated identity against visible bypass actors and reports conservative branch-policy findings. Hidden bypass lists and inaccessible classic protection are reported as unknown. It still exits unsuccessfully because those observations do not establish all prerequisites for strict landing. The command has only been tested with a local GitHub stub; the separate GraphQL ref-update probe described in the protocol used a user credential and temporary unprotected branches.

To try webhook intake locally, set `SLUSS_WEBHOOK_SECRET` in the environment and run `cargo run -- serve`. It listens on `127.0.0.1:8080` by default; `--listen` changes the address. External traffic requires a trusted HTTPS reverse proxy. Without configuration, this only records deliveries.

With a configured installation and repository, security-related webhook hints also invalidate active batch evidence and old CI-only holds before scheduling reconciliation. Installation-wide and organization ruleset events without a repository are routed conservatively to that configured repository. Already running jobs and reservations still need cancellation and recovery. Membership and team events depend on GitHub App subscriptions and permissions; delayed or missing events mean fresh checks remain necessary.

To enable the experimental observer, copy [examples/sluss.toml](examples/sluss.toml) to an operator-controlled location, set `SLUSS_WEBHOOK_SECRET` and `SLUSS_GITHUB_PRIVATE_KEY_PATH`, then run `cargo run -- serve --config /path/to/sluss.toml`. Startup and periodic scans recover missed notifications, and failed work remains queued for retry. Only the configured repository is processed. This path has only been tested with a local GitHub stub; do not deploy this preview as a production GitHub App.

Add `--auto-plan` to the configured service to create batches automatically from its reconciled queue. The queue configuration controls maximum batch size, concurrent active batches, debounce and collection window; see [the example](examples/sluss.toml). The first automatic planning pass binds these settings to the database, and conflicting manual or automatic planners fail closed. Changing bound settings requires an explicit migration, which is not implemented yet. `sluss status` shows active batch IDs and states after restart. With planning alone, batches stop at `Planned`; no batch authorizes a merge.

For experimental automatic staging on GitHub.com, add `--auto-stage --policy-file .github/workflows/sluss-ci.yml` to `serve`, repeating `--policy-file` for every operator-trusted policy file. Sluss refreshes admission, fetches the target and [GitHub PR head refs](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally), compares their SHA values with the frozen batch, and builds in disposable Git repositories before publishing the staging ref with a separately scoped App token. Policy paths are bound to the database; conflicting lists fail closed and migration is not yet implemented. Staging requires trusted branch rules that constrain the App, isolated runners, and operator control of the complete policy-file list. This path has been tested with local Git repositories and a GitHub API stub, but fetching and publishing with a real GitHub App have not been validated. Automatic staging does not start CI or authorize landing. Add `--verification-policy /path/to/verification.toml` to calculate the selected suites from the integration commit during staging. The selection and the transition to `Testing` are committed atomically, including after a restart. The same option must be supplied to automatic dispatch; the example workflow only supports `full`, so selective use requires an operator-protected suite mapping. The first staged batch binds full-versus-selective mode and the selective policy digest to the database; changing them requires the explicit drained migration below.

To opt into automatic dispatch, add `--auto-dispatch --capacity /path/to/capacity.toml --workflow-id <id> --required-job test --pool rust=1` to `serve`. Enable `--observe-dispatches` separately to read results. The same admission, target, runner-inventory and durable dispatch checks apply as for the manual command. The worker does not retry a dispatch once its send may have occurred; uncertain starts require reconciliation. CI-only batch completion and capacity release are separate opt-ins; this preview is not an unattended production queue. A selective batch also needs `--verification-policy` and a trusted workflow implementing its suite mapping.

For experimental cancellation of known runs after their batches are invalidated, add `--cancel-stale --capacity /path/to/capacity.toml` to `serve --config ...`. Sluss requests normal GitHub cancellation once and keeps capacity reserved; a missing response remains uncertain and is not blindly retried. `sluss cancel-stale` performs the same check manually. Neither path has been tested against a real GitHub App or runner.

For development, `sluss reconcile --help` describes a manual, one-shot reconciliation command. It requires `SLUSS_GITHUB_PRIVATE_KEY_PATH` and explicit, operator-controlled App, installation and repository IDs. It reads all open PRs and their reviews, checks reviewer permissions, and atomically updates local queue observations if no newer event arrived. This path has only been tested with a local GitHub stub. A database is bound to one repository and policy; a policy change fails closed and currently requires an explicit migration that is not yet implemented.

For an experimental local Git exercise, reconcile a repository first, then freeze an observed base and prepare an integration in a local bare staging repository:

```sh
sluss --db sluss.sqlite plan --id batch-0123456789abcdef --base-sha <base-sha> --debounce-seconds 60 --batch-window-seconds 60
sluss --db sluss.sqlite prepare-local --batch-id batch-0123456789abcdef --source /path/to/source --staging-remote /path/to/staging.git --policy-file .github/workflows/ci.yml
```

The manual planner waits for a partial batch until the oldest selected candidate has been stable for the debounce interval plus the collection window. A full batch and bisection halves do not wait for the collection window. The timestamps survive restarts and depend on the host clock; the optional automatic planner uses the same rules.

The operator must obtain the target base SHA and list every policy file; the planner rejects a base different from the last successful GitHub reconciliation. That observation can become stale immediately; manual dispatch refreshes it, and strict landing will require a separate final check. The source must contain the frozen commit objects. Preparing a batch does not start CI or grant merge permission. The local staging remote must be trusted and must not trigger unintended workloads. This path is for development and has not been validated against a live GitHub App.

A prepared GitHub staging batch can be dispatched explicitly with `sluss dispatch-github --batch-id <id> --config /path/to/sluss.toml --capacity /path/to/capacity.toml --pool rust=1 --workflow-id <id> --required-job test`. The capacity file describes global pool limits and physical machines; see [the example](examples/capacity.toml). The selected host's unique `sluss-host-*` label is passed as the workflow input in [this single-job example](examples/github-actions/sluss-ci.yml). `sluss observe-dispatch --help` describes how to compare the reported runner against the host's configured runner IDs; `sluss serve --config /path/to/sluss.toml --capacity /path/to/capacity.toml --observe-dispatches` can periodically observe known receipts and retry failed reads after restart; `sluss cancel-dispatch` only releases a reservation that has not been claimed. This path has been exercised with a local GitHub stub, not GitHub or real runners. Before dispatch, Sluss refreshes PR and review admission, requires the bound repository policy and target base to match, and checks the target branch around its staging-ref read. It also reads the workflow registration twice, requires the workflow to be active, and checks that its exact file path was included in the batch's frozen policy-file list. The workflow path is saved atomically with the dispatch claim and compared to later run observations; older in-flight dispatches without this binding are handled as historical CI-only observations. A pre-existing staged batch without that list is refused and needs to be rebuilt. These non-atomic provider reads cannot prevent a later change and do not authorize landing. Sluss also reads the repository runner register using a separate Administration-read App token and compares it with the configured IDs and labels. A busy host does not block dispatch to another host whose full configured slot budget is idle; an existing reservation stays bound to its original host. Organization and enterprise runners are not covered, and physical placement remains operator-supplied. Correct host labels, trusted workflow contents, isolated runners and rerun restrictions remain operator prerequisites; observation does not release capacity or authorize landing.

For a conservative selective-verification preview, `sluss select --policy /path/to/verification.toml --source /path/to/repo --base-sha <base> --head-sha <integration>` compares two commit trees and prints affected suites. See [the policy example](examples/verification.toml). Unknown paths, sensitive Git and Rust configuration, and any affected component without suites select the full configured suite; submodule pointer changes are included even if local Git configuration hides them. The operator must maintain the complete dependency graph and policy outside PR-controlled paths. The selection algorithm version is part of the policy digest: a database bound to the previous preview requires a migration before selective staging can resume.

To migrate a selection policy, first reconcile or release all reservations and unresolved dispatches through their normal recovery paths. Drain active batches, run `sluss pause`, stop all Sluss workers and any manual staging or dispatch processes, and read the current selection mode from `sluss status` (which may be `unbound` for a manually selected preview batch). Then run `sluss migrate-selection --expected-mode <current-mode> --policy /path/to/verification.toml`; use `--full` instead of `--policy` to switch to full verification. If old batches cannot be drained, `--discard-unstarted` explicitly invalidates them so their PRs can be planned again; it never releases a reservation or permits an unresolved dispatch. The command checks the expected mode, pause state and durable work records in one transaction. It marks prior CI investigations stale, clears CI-only holds and incomplete scheduling-delay intervals, and records the transition; unrelated integration-conflict work and historical completed batch records remain. Sluss stays paused until `sluss resume`. The database cannot establish whether an external Git process is still publishing or a staging ref triggered a workflow, so stopping workers and controlling staging triggers are operator prerequisites. The same-mode `--discard-unstarted` option can rebuild an older staged batch that lacks a frozen policy-file list; cancel any prepared reservation first. The migration does not change policy-file lists, capacity topology or the CI investigation setting.

After staging, `sluss select-batch --batch-id <id> --policy /path/to/verification.toml --source /path/to/repo` freezes the selected suites with the base, integration SHA and policy digest. The source repository must contain both commits, including the staged commit. Supply the same policy as `--verification-policy /path/to/verification.toml` to `dispatch-github`; a changed policy or batch stops dispatch. Without a frozen selection, dispatch passes `full`. The workflow receives the sorted, comma-separated suite names as `sluss_suites`. The example workflow intentionally supports only `full` and fails for selective inputs: an operator must implement and protect their own trusted suite mapping before using selective dispatch. A selection and its input do not establish workflow trust, constitute CI attestation, or authorize landing. Existing preview dispatch records without suite names fail closed and need explicit recovery.

If a dispatch may have been sent but its response was lost, an operator can identify a candidate GitHub run and invoke `sluss recover-dispatch --batch-id <id> --run-id <run> --config /path/to/sluss.toml --capacity /path/to/capacity.toml`. Sluss checks the exact provider run, workflow, repository, branch, commit and first attempt before recording the ID; it never resends the request. The record is marked `recovered` because matching metadata does not prove the uncertain request created that run. Recovery neither authorizes landing nor releases the reservation. A directly received run ID is marked `direct`; older preview records may have an unknown source.

For CI-only scheduling, add `--complete-ci-only` alongside `--observe-dispatches`. After a directly received run has a completed first-attempt provider observation, Sluss retires the scheduling batch and holds its unchanged PR heads until their inputs change; this holds for both successful and failed outcomes and does not grant merge approval or classify a failure as a bad PR. `sluss retry-ci --batch-id <id>` clears those holds. Runner reservations remain held unless the separate conservative release option is enabled. Recovered or legacy-unknown run IDs are observed but are not completed automatically.

To investigate failed CI-only batches, add `--bisect-ci-failures` with `--complete-ci-only --observe-dispatches` and enable the planner, staging and dispatch workers needed to run the resulting halves. Sluss tests both halves and only continues into a failing half when its sibling succeeded with comparable frozen inputs and CI policy. Both failures, both successes, different policies or suites, and non-failure conclusions stop the investigation as inconclusive. Changed inputs make it stale. A failing singleton is marked for review, not identified as guilty; infrastructure failures and interactions between changes remain possible. Split batches use the full configured suite list so their results can be compared. This is scheduling assistance, not merge approval or trusted attestation. The first CI-only worker permanently binds this option in the database; changing it requires a migration that is not yet implemented.

For an experimental bounded CI-only release, add `--release-ci-only` with `--complete-ci-only --observe-dispatches`. It rechecks the exact completed run, observed placement and repository runner inventory before releasing its reservation. It can also release a directly identified run belonging to an invalidated batch once that run is completed; completed jobs on the confirmed runner are counted in metrics, while a run cancelled before any job starts may have no placement. Unknown or operator-recovered run identities remain reserved. This mode requires exactly one configured runner and one slot per physical host, and each global pool budget must cover the sum of that pool's host capacities. GitHub runs only one job at a time per runner, so this conservative envelope reserves enough pool capacity even if an old workflow is rerun. The operator must ensure each host has no additional runner process, all work on that host stays within its declared pool capacities, no untracked workloads use the same global pools, and completed jobs cannot leave work running; GitHub inventory cannot verify physical colocation, other runner scopes or process cleanup. The first release permanently binds the capacity topology in this preview; changing it requires a migration not yet implemented. This has only been tested against a local provider stub, not real runners, and it does not authorize landing.

The expected GitHub job names are frozen in each dispatch. `observe-dispatch` compares the provider result with those names, the exact run and commit, the reserved host and the current batch. Sluss stores the observed run and normalized job records for completed comparisons; `sluss ci-evidence --batch-id <id>` displays them and any persistent conflict. A later contradictory snapshot blocks CI-only completion and capacity release; older summaries without a job snapshot are retained without inventing missing details. These records do not issue `sluss/verified` or authorize a merge. Trusted workflow policy and branch protections are not yet established.

`sluss metrics` sums actual start-to-finish time for completed, host-checked jobs observed by Sluss. Repeated reads of the same job do not double count it. It also reports completed scheduling-delay intervals grouped by requested pool: from the first failed capacity observation to a later eligible reservation, including polling gaps, pauses or outages. A request for multiple pools appears under each pool; this is not proof that any specific pool was saturated and must not be summed as runner time. Incomplete intervals and requests never attempted by the scheduler are excluded. Both measures use partial observations; jobs Sluss has not observed, unverified placement and rerun attempts are excluded, and delivered PRs and per-PR savings are not yet reported.

`sluss benchmark --input examples/benchmark.json` demonstrates a separate before/after report using **synthetic data**. For a real pilot, operators must collect complete job attempts and delivered PRs independently and describe the cohort boundaries and omissions. The command reports runner time per delivery, reruns, optional run-to-PR associations and ready-to-merge samples; it does not validate the source data or prove savings. See [pilot measurement](docs/benchmark.md).

The database defaults to `sluss.sqlite` in the current directory; use `--db PATH` to select another. The pause flag and observations survive restarts; pause also stops the experimental batch planner. Queue entries must eventually be reconciled against GitHub; an observation is never an approval.

## Intended operation

* **CI-only:** schedule existing workflows without changing merge behavior. A batch result is not a per-PR merge approval.
* **Strict merge:** build an integration on a frozen base and PR heads, verify that exact commit, recheck all authorization and policy, and update the target only if the update preserves the required invariants. No silent fallback to squash or ordinary GitHub merges.

Sluss must remain independent of any specific repository. See [architecture](docs/architecture.md), [protocol](docs/protocol.md), and [security](docs/security.md) for the design and open work.
